## 1. 全体像

### 1.1 登場人物（3つのプログラムが連携している）

今回いじったダッシュボードは、実は **3つの独立したプログラム** の上に乗っています。

```
[あなたのブラウザ（スマホ/PC）]
        │  HTTP（http://razer:8080/dashboard）
        ▼
[status_api.py]  ← razer-server で常駐（ポート8080）。今回の主役。
        │  ・温度やCC利用率を返す
        │  ・「CC発話通知」フラグの ON/OFF を持つ  ★ここがミソ
        │  ・/control/* を下の gateway へ「中継（プロキシ）」する
        ▼
[gateway]  ← 別プログラム（ポート8767）。StackChan 本体を操作する。
        │  ・モード（プリセット）の保存先はこっち
        ▼
[StackChan 実機]
```

**重要な事実**: 「モード（設定一式の保存）」は **gateway 側** に保存されます。一方「CC発話通知の ON/OFF」は **status_api.py 側** が持っています。**置き場所が違う** — これが今回の問題の核心です。

### 1.2 なぜ CC通知はモードに入っていなかったのか

前回モード機能を作ったとき、保存される設定は gateway が自分で集めていました（音量・明るさ・LED・近接・heartbeat など）。
ところが **CC発話通知のスイッチは gateway の管轄外**。gateway はその存在すら知りません。だから:

- モードを保存しても、CC通知の状態は記録されない。
- モードを適用しても、CC通知は変わらない。

ユーザーから見ると「CC通知だけモードに反応しない」。これが今回の出発点でした。

### 1.3 なぜ「別々」になっているのか（意図的な設計）

「じゃあ gateway に CC通知も持たせれば？」と思いますよね。でも**わざと分けてあります**。

CC発話通知は「Claude Code や Codex が喋るときのスイッチ」で、**hook（フック）** という別の仕組みが見るフラグです。StackChan のデバイス設定（音量など）とは出自がまったく違う。混ぜると、Claude Code 都合の変更が StackChan の gateway を揺らしてしまう。だから「**別系統**」として切り離してあるのです。

> **設計の勘どころ**: 「動かすために一番簡単な置き場所」と「あるべき置き場所」は違うことがある。今回は後者（別系統を保つ）を選び、その制約の中で 1 を実現しました。

## 2. 採用した考え方の解説

ここでは今回使った発想を「何か→なぜ→喩え→使った場面」の4点セットで説明します。

### 2.1 プロキシ — 「電話の取次（とりつぎ）係」

- **何か**: ブラウザからのリクエストを受け取り、別のサーバー（gateway）へ転送して、返事をそのまま渡す中継役。
- **なぜ必要か**: ブラウザは gateway（:8767）へ直接話せない（認証トークンが必要・別ポート）。間に立つ status_api が代わりに話す。
- **喩え**: 会社の代表電話。あなた（ブラウザ）は内線番号を知らなくても、受付（status_api）が担当部署（gateway）へ繋いでくれる。
- **使った場面**: `/control/presets/save` などのモード操作は、status_api が gateway へ取り次いでいます。

### 2.2 サイドカー — 「本のしおり・付箋」

- **何か**: 本体（gatewayのモード保存ファイル）には手を入れず、**隣に置く小さな別ファイル**で足りない情報を補う手法。
- **なぜ必要か**: gateway のモードファイルに CC通知を書き足すと、gateway 本体の改造＋テスト816件のやり直し＋再起動が必要になる。それを避けたい。
- **喩え**: 図書館の本（gatewayのモード）に直接書き込むのは禁止。だから付箋（サイドカー）に「この本を読むときは照明を暗めに」とメモして挟んでおく。本は無傷。
- **使った場面**: `~/.stackchan/preset_cc_notify.json` という付箋ファイルに「モード名 → CC通知ON/OFF」を記録。

```json
// preset_cc_notify.json の中身（イメージ）
{ "おやすみ": false, "つうじょう": true }
//   モード名      CC通知の状態（false=OFF）
```

### 2.3 フラグファイル — 「あるか無いかで意味を持つ目印」

- **何か**: ファイルの中身ではなく、**存在するかどうか** で状態を表す仕組み。
- **なぜ必要か**: 「CC通知 OFF」をシンプルに表現できる。複雑なDBは要らない。
- **喩え**: ドアノブに掛ける「起こさないでください」の札。札が掛かっていれば（ファイルが在れば）OFF、外せば（ファイルが無ければ）ON。
- **使った場面**: `~/.claude/hooks/stackchan_notify.off` が**在る=OFF / 無い=ON**。今回 `set_cc_notify(enabled)` 関数でこの札を掛け外しします。

### 2.4 関心の分離（別系統）— 「キッチンとレジは別管理」

- **何か**: 性質の違うものは混ぜずに別管理する設計原則。
- **なぜ必要か**: 片方の都合の変更が、もう片方を壊さないようにするため。
- **喩え**: 飲食店でキッチン（gateway=デバイス設定）とレジ（status_api=Claude Code通知）を別の人が担当する。レジの締め作業がキッチンを止めない。
- **使った場面**: CC通知を gateway に持ち込まず、status_api 側で完結させた判断そのもの。

## 3. 工程の流れ（やったことを時系列で）

### 工程1: Task 1 — CC通知をモードに連動（`status_api.py`）

やったことは「**モード操作を取り次ぐついでに、付箋（サイドカー）を更新する**」だけです。

| 操作 | 取次のついでにやること |
|---|---|
| モード保存（save） | 「今のCC通知状態」を読み、付箋に `モード名→状態` を記録 |
| モード適用（apply） | 付箋にそのモードの記録があれば、CC通知の札を掛け直す |
| モード削除（delete） | 付箋からそのモードの記録を消す |

コードの要点は「**取り次ぐ処理**」と「**ブラウザに返す処理**」を分けたこと。間に付箋更新を挟めるようにするためです。

```python
# 取り次ぎ（gatewayへ投げて結果をもらうだけ。まだブラウザに返さない）
status, payload = self._forward_control("POST", path, body)

# 成功したときだけ、付箋を更新（＝CC通知をモードに連動）
if name and status == 200 and self._payload_ok(payload):
    if path == "/control/presets/save":
        m = load_preset_cc(); m[name] = cc_notify_enabled(); save_preset_cc(m)
    elif path == "/control/presets/apply":
        m = load_preset_cc()
        if name in m: set_cc_notify(bool(m[name]))   # 札を掛け直す
    # ... delete も同様

# 最後に gateway の返事をそのままブラウザへ
self._send(status, payload, "application/json; charset=utf-8")
```

ポイントは **「保存ボタンの送信内容は一切変えていない」** こと。ブラウザは今まで通り `{名前, 上書き}` だけ送ります。status_api が取次の瞬間に**自分で**「今のCC通知状態」を読んで記録するので、「現在の設定を保存」という言葉の意味（＝今の状態をまるごと保存）にちゃんと合います。

### 工程2: Task 2 — サーバータブにモード切替を追加（`dashboard.html`）

サーバータブの一番下（利用率の後）に「ドロップダウン＋適用ボタン」を足しました。保存・削除はスタックちゃんタブのままです（要望が「切り替え」だったので）。

ここで効いたのが **関数の一般化**。元々モード一覧をドロップダウンに流し込む処理は1個分しか想定していませんでした。それを「複数のドロップダウンに同じ内容を流す」形に書き換え、コードを二重に持たないようにしました（DRY = Don't Repeat Yourself＝同じことを繰り返し書かない）。

```javascript
// 2つの select を同じ一覧で更新する（sc=スタックちゃん, srv=サーバー）
[['sc-preset-select', 'sc-preset-apply', 'sc-preset-delete'],
 ['srv-preset-select', 'srv-preset-apply', null]].forEach(([selId, applyId, delId]) => {
   // ... それぞれの select に option を流し込む
});
```

### 工程3: Task 3 — モード欄を一番下へ（`dashboard.html`）

スタックちゃんタブの「🎚 モード」カードを、一番上から一番下（デバイス調整の後）へ**位置だけ移動**。中身（ボタンや ID）は1文字も変えていません。HTML は「書いてある順番＝画面に出る順番」なので、ブロックを切り取って貼り直すだけです。

### 工程4: 検証

- **status_api.py の関数を単体テスト**（サービスを止めずに）: 札の掛け外し・付箋の読み書き・保存→適用での復元、すべて期待通り（ALL OK）。
- **HTMLの構造チェック**: タグの開閉数が一致（section 11=11）、IDの重複なし。
- **ライブ配信の確認**: ブラウザが受け取るHTMLが更新後の内容になっていることを確認。

## 4. 設計判断の記録

### 判断1: CC通知をどこに持たせるか

| 案 | 内容 | 判定 |
|---|---|---|
| **A. status_api にサイドカー** ✅ | 付箋ファイルで「モード名→CC通知」を記録 | **採用**。別系統を保ち、gatewayに触れない。razer-server に1つなので全端末で共有される |
| B. gateway のモードに同梱 | モードファイルに cc_notify を書き足す | 不採用。gateway改造＋テスト816やり直し＋再起動。別系統設計も崩れる |
| C. ブラウザのlocalStorageに保存 | 各ブラウザに記憶 | 不採用。端末ごとにバラバラになり「共有モード」の意味が消える |

### 判断2: サーバータブの「保存・削除」は付けるか

- 要望は「**切り替え**ができるように」。→ 切り替え（適用）だけ付け、保存・削除はスタックちゃんタブに集約。**画面ごとに役割を絞る**ほうが迷わない。

### やらなかったこと（意図的に）

- **gateway には一切触れていない**。今回の3要望はすべてダッシュボード側（status_api.py + dashboard.html）で実現できると分かったため。触る範囲を最小にするほど、壊すリスクも小さい。
- **既存の保存ロジック（ブラウザ側）も変えていない**。連動は取次役（status_api）に寄せた。

## 5. 用語集

| 用語 | 一言で | 喩え |
|---|---|---|
| プロキシ（proxy） | リクエストの中継役 | 会社の代表電話・取次 |
| サイドカー（sidecar） | 本体を触らず隣に置く補助ファイル | 本に挟む付箋 |
| フラグファイル | 存在の有無で状態を表すファイル | ドアの「起こさないで」札 |
| 関心の分離 | 性質の違うものを別管理する | キッチンとレジの担当を分ける |
| hook（フック） | ある動作の前後に差し込む処理 | Claude Codeが喋る瞬間に割り込む仕掛け |
| DRY | 同じ処理を二度書かない | 一つの型で複数を量産 |
| graceful degradation | 一部失敗しても全体は止めない | 付箋が無くても本は読める |
| 単体テスト | 部品だけを切り出して動作確認 | サービス本体を起動せず関数だけ試す |

## 6. 残っていること（あなたの操作が必要）

コードは完成済みですが、**最後の2手はケンジさんの操作**が必要です（私には sudo パスワードが無いため）。

1. **status_api を再起動**（Task 1 のバックエンドを有効化）。プロンプトに次を貼って実行:
   ```
   ! sudo systemctl restart status-api
   ```
   ※ dashboard.html（Task 2/3 の見た目）は再起動不要で、ブラウザ更新だけで反映されます。

2. **ブラウザで動作確認**:
   - Task1: スタックちゃんタブで CC通知を OFF → モードを保存 → CC通知を ON に戻す → そのモードを適用 → CC通知が OFF に戻ればOK。
   - Task2: サーバータブの一番下にモード切替が出て、適用できる。
   - Task3: スタックちゃんタブの一番下にモード欄がある。

> **注意（既存モード）**: 今ある「おやすみ / つうじょう / サポート」は今回の機能より前に作られたので、付箋に記録がありません。適用してもCC通知は変わりません。**CC通知も連動させたいモードは、一度保存し直す**と今の状態が記録されます。
