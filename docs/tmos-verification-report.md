## 1. 全体像

### 1.1 何をしたか（一言で）

新しく届いた**熱を見るセンサー**を StackChan に繋いで、「部屋に人が居るかどうか」を
数値で判定できるか実機で確かめました。結論は **強い GO（採用合格）** です。

具体的には:

1. firmware には一切手を入れず、PC 側（gateway）から I2C 経由でセンサーを読む経路を作った
2. センサーが正しく繋がり、人体に強く反応することを確認した
3. 致命的なバグ（**読み裂け**）を発見して直した
4. 本番実演（8分・961サンプル）で「**静止した人を 211 秒連続で『居る』と保持**」を実証した
5. 「在室している時だけ StackChan が一言つぶやく」機能（heartbeat 在室ゲート）に使える、と判定した

### 1.2 なぜやったか — 「会話に割り込まない」ための土台

このプロジェクトには**絶対に守る設計原則**があります。その第1条が
**「人の会話に割り込まない」**。StackChan が好き勝手に喋り出すのは厳禁です。

一方で Phase D / E では「ふとした時に StackChan が一言つぶやく」heartbeat 機能を
作りました。この2つを両立させる鍵が **在室ゲート** です:

```
「人が部屋に居る時だけ、つぶやいてよい」
　　　　└─ "人が居るか" を機械的に判定する目が要る → それが TMOS
```

問題は、**人はいつも動いているわけではない**こと。ソファで本を読んでいる人は
ほぼ静止しています。普通の人感センサー（後述の焦電 PIR）は「動き」しか見ないので、
静止した人を「居ない」と誤判定してしまう。そこで**静止した人も検知できる**
TMOS が候補に挙がりました。

### 1.3 データの流れ（構成図）

検証は firmware を書き換えず、PC 側から I2C をリモート操作して行いました:

```
[検証スクリプト  scratch/tmos_probe.py]   ← Python・トークン不要
   │  POST /control/i2c  {"op":"write_read", "addr":0x5A, ...}
   ▼
[ダッシュボード proxy  status_api.py :8080]  ← ローカル無認証・Bearer を注入して中継
   │  POST /control/i2c   (+ Authorization: Bearer ***)
   ▼
[gateway  http_server.py :8767]            ← 本体（systemd 常駐）
   │  control_i2c → i2c_write_read → WebSocket MCP
   ▼
[StackChan firmware] ── Grove Port.A I2C バス(400kHz) ──►
   [PaHUB2 mux @0x70] ─ ch3 → TMOS PIR (STHS34PF80 @0x5A)
```

「センサーの値を読む」というたった1つの操作のために、4段の中継を通っています。
なぜこんな遠回りをするのか、は章2.5で説明します（一言で言うと**鍵に触らずに
外から覗ける窓**を作りたかったから）。

## 2. 採用した技術・概念の解説

### 2.1 TMOS — 「動かなくても『居る』が分かる、温度の目」

- **何か**: STMicro 製の赤外線サーモパイル（型番 STHS34PF80）。物体が出す
  赤外線（＝熱）の量を測るセンサーです。"TMOS" は Thermal MOS の略。
- **なぜ必要か**: 人間は体温で常に赤外線を出しています。カメラと違って
  暗闇でも、相手が静止していても、その「熱の存在」を捉えられます。
- **喩え**: 暗い部屋でも手をかざすと暖かさで「あ、そこに居るな」と分かる感覚。
  目（可視光）ではなく**温度で存在を感じる**センサーです。
- **使った場面**: 「部屋に人が居るか」を判定する在室ゲートの目として。

### 2.2 焦電 PIR との違い — 「動き」か「存在」か

世の中で「人感センサー」と言うと、たいていは**焦電型 PIR**（トイレや玄関灯の
あれ）です。これは赤外線量の**変化＝動き**を検知します。だから人が静止すると
明かりが消える。「トイレで動かないでいると電気が消える」あの現象です。

TMOS は内部アルゴリズムで **presence（存在）** と **motion（動き）** を
**別々に**出します。これが決定的な差で、**presence は静止した人でも出力が続く**。
在室ゲートに必要なのはまさにこの「動かなくても居ると分かる」性質でした。

> **教訓**: センサー選びは「何を検知するか」より「**何を検知し続けられるか**」が
> 効くことがある。動きベースの安いセンサーで在室ゲートを作っていたら、
> 静かに本を読む人を「不在」と誤判定して、つぶやくべき時に黙っていたはずです。

### 2.3 I2C と「読み裂け」 — 「2回に分けて読むと値が混ざる」

- **I2C（アイ・スクエア・シー）とは**: 1本の線で複数のセンサーと会話する通信規格。
  「アドレス 0x5A さん、0x3A 番地の値ちょうだい」という問い合わせを送ると、
  センサーが値を返します。
- **16ビット値の罠**: presence のような大きな値は 2バイト（下位 L + 上位 H）に
  分かれて格納されています。これを **L と H で別々に2回読む**と事故が起きます。
  センサーは 4Hz（250ミリ秒ごと）で新しい値に書き換わるので、L を読んだ直後・
  H を読む前に更新が走ると、**古い L と新しい H が混ざった偽の値**になるのです。
  これを **読み裂け（torn read）** と呼びます。
- **対策**: L と H を**1回の通信でまとめて2バイト読む**（連番レジスタの
  オートインクリメント機能を使う）。これで「同じ瞬間の L と H」が保証されます。

`gateway/stackchan_mcp/sensors.py` の読み取り関数が、まさにこの「1トランザクション
2バイト読み」を実装しています:

```python
async def _read(dispatch, addr, reg, n):
    # ポインタを reg にセットして n バイトを ONE トランザクションで読む。
    # L/H を別々の通信に割ると ODR 更新を跨いでゴミになる。
    payload = await dispatch("i2c_write_read",
                             {"addr": addr, "write_bytes": [reg], "n_bytes": n})
    ...

def _s16(lo, hi):  # 2つのリトルエンディアン・バイト → 符号付き16bit
    val = (hi << 8) | lo
    return val - 0x10000 if val >= 0x8000 else val
```

### 2.4 PaHUB2 / I2C mux — 「1本の線を8股に切り替えるスイッチ」

- **何か**: PCA9548A というチップを積んだ「I2C マルチプレクサ（mux）」。
  1本の I2C バスを 8チャンネルに分岐します（製品名 PaHUB2）。
- **なぜ必要だったか**: TMOS とジェスチャーセンサーを同時に繋ぎたいが、両者が
  たまたま近いアドレスでも衝突しないよう、**物理的にチャンネルを分けて**おける。
- **喩え**: 1本の電話回線を 8本の内線に切り替える交換機。「3番に繋いで」と
  指定（`1 << 3` を mux に書く）してから話す。
- **使った場面**: ch3 に TMOS、ch2 にジェスチャーセンサーを配置。読むたびに
  「まず ch を選択 → それから読む」を繰り返します。

### 2.5 /control/i2c — 「鍵に触らず外から覗く窓」（道A）

- **何か**: 検証のために gateway へ1本だけ足した HTTP エンドポイント。
  外から `POST /control/i2c` を投げると、その I2C 操作を firmware に転送します。
- **なぜ作ったか**: firmware を書き換えてセンサー専用ドライバを入れる（=「道B」）
  のは重い作業です。一方、汎用 I2C 操作を外から叩ければ、**firmware 改造ゼロ**で
  どんなセンサーでも試せます。この「外からリモートで I2C を叩く」方針を **道A** と
  呼んでいます。
- **巧い点**: ダッシュボードの proxy（`:8080`）が `/control/*` を素通しして
  認証トークンを自動で足してくれるので、検証スクリプトは**秘密の鍵に一切触れず**に
  `:8080/control/i2c` を叩くだけで済みます。

## 3. 工程の流れ（時系列）

### 工程1: 疎通確認 — 「そこに居ますか？」

mux 越しに ch3 を選び、TMOS に「あなた誰？」（WHO_AM_I レジスタ 0x0F）を尋ねると
`0xD3` が返りました。これは STHS34PF80 の固有の身分証番号。**正しく繋がっている**
ことの確認です。

### 工程2: 無人ベースライン — 「誰も居ない時の数値」

人が居ない状態で 15分間ポーリングし続けて、ノイズの幅を測りました。presence は
±30 程度の小さなノイズ帯、存在フラグ（PRES）は **15分間まったく発火せず**。
「誰も居ない時はちゃんと『居ない』と言う」= 在室ゲートに好適な静かさです。

### 事件簿1: presence が ±256 に張り付く — 読み裂けの発覚（最重要）

最初のバージョンでは、presence の値が**常に ±256 の範囲に張り付く**奇妙な症状が
出ました。人が近づいても大きく振れない。

**調査**: 同じく16bitの `obj_raw`（物体の生の赤外線値）は 255 を超える値を返せて
いました。つまり**通信自体は健全**。違いは読み方だけ — presence は L と H を
**2回に分けて**読んでいたのです。

**原因**: 章2.3の読み裂け。H バイトが 0x00/0xFF の境界しか跨がない見え方になり、
`+247 → -248` のような偽スパイクが出ていた。

**修正**: L+H を**1トランザクションの2バイト読み**に変更。STHS34PF80 が
連番レジスタをオートインクリメントで返すことを実機で確認しました。

> **教訓**: マルチバイトのセンサー値は必ず1回の通信でまとめて読む。
> 「読めてはいるが値が変」な時は、通信エラーより先に**読み方のタイミング**を疑う。
> BDU（Block Data Update）も「同一読み取り内での一貫性」しか保証しないので、
> 分割読みには無力です。

### 工程3: ハブ構成への変更 — mux か、パッシブか

「正しい検証のため」TMOS を直挿しから **PaHUB2(mux) 経由**に配線変更しました。
すると scan で見えるのが **0x70（mux 自身）だけ**になり、下流のセンサーが消えた。
全8チャンネルを順に選択して scan し直して、ch3=TMOS / ch2=ジェスチャー を発見。

> **教訓**: M5Stack の「I2C 拡張ハブ」には、製品名が似ていても **mux(PCA9548A)** と
> **パッシブ分岐** の2系統がある。見分け方は一発 — scan して **0x70 系だけ**なら mux
> （チャンネル裏に隔離）、**下流アドレスが直接見える**ならパッシブ。今回は mux でした。

### 事件簿2: ジェスチャーセンサーが最初の問いかけを無視する

mux の ch2 を scan してもジェスチャーセンサー（PAJ7620U2）が応答しない。
原因は故障ではなく**スリープ**でした。このセンサーは**寝ている間、最初の I2C
アクセスには ACK を返さない**（I2C 活動そのもので起きる）仕様。各チャンネルを
**二度読み**（1回目で起こす → 2回目で読む）したら part_id `0x7620` を確認できました。

### 工程4: 本番実演 — 8分・961サンプルの決定的データ

ケンジさんがセンサーのレンズを自分に向け、「無人 → 接近 → 正面50cmで静止 →
手振り → 離脱」を実演。閾値はデフォルト（200）のまま:

| 区間 | presence の平均 | PRES フラグ | 評価 |
|---|---|---|---|
| 無人ベースライン（473サンプル≒5分） | **-1**（±130 ノイズ） | **誤発火 0回** | 静か |
| 在室（451サンプル） | **767**（134〜1187） | **100% 点灯** | 強い |

ここから3つの合格ポイントが出ました:

- **静止在室の保持＝合格**: 在室の1ブロックで **211.7 秒連続で PRES 100% 点灯**
  （平均774）。静止しても減衰せず保持し続けた。初回検証で見えた「減衰」は、
  人が通過する過渡現象で、定常状態ではなかったと判明。
- **クリーンな分離**: 無人 平均 -1 に対し在室 平均 767。**50倍超の差**で、
  閾値200がちょうど中間に位置する。誤判定の余地が小さい。
- **速い解除**: 人がフレームから外れると presence は**1〜2秒で 200 未満に復帰**
  （84→49→31→…→8）。「居なくなったら速やかに黙る」も満たす。

この検証結果が、`sensors.py` の在室判定ロジックにそのまま反映されています:

```python
return {
    "present": pres_flag or presence > PRESENCE_THRESHOLD,  # ← 在室の定義
    "presence": presence,
    "motion": motion,        # 参考値（在室判定には使わない／2.6参照）
    ...
}
```

## 4. 設計判断の記録

### 4.1 在室判定に presence を使い、motion は使わない

| 信号 | 静止した人 | 無人時の誤発火 | 在室ゲートに採用？ |
|---|---|---|---|
| **presence（存在）** ✅ | 検知し続ける | **0/473（なし）** | **採用** |
| motion（動き） | すぐ消える | 46/473（あり） | 不採用（参考値のみ） |

motion フラグは**無人でも時々誤発火**しました（熱ノイズの揺らぎ）。在室ゲートに
使うと「誰も居ないのに居る」と誤爆します。だから在室の定義は
**`PRES フラグ または presence > 200`** に固定しました。

### 4.2 検証経路は「道A（リモート I2C）」、firmware ドライバ化（道B）は保留

| 経路 | 内容 | 判断 |
|---|---|---|
| **道A: /control/i2c** ✅ | PC から I2C をリモート操作 | firmware 改造ゼロ・即試せる。**採用** |
| 道B: firmware ドライバ | C++ で専用ドライバを焼く | 速いが重い・リビルド必須。**保留** |

「まず軽い経路で価値を確かめ、必要になってから重い実装をする」。検証段階では
道A で十分でした。常用で速度が要るなら道B に格上げを検討します。

### 4.3 やらなかったこと（意図的に）

- **presence 閾値のチューニング**: デフォルト200が分離の中点にぴったりだったので、
  AN5867 が解説する LPF/閾値の微調整は不要でした。「デフォルトで足りるなら触らない」。
- **距離1m/2m・横ずれ FOV の定量化**: 在室ゲートの採否判定には不要なので後回し。
- **ジェスチャー9種の動作検証**: TMOS とは別タスク（センサータブ側）に切り分け。
- **ToF（VL53L0X）での視線追従**: 部屋スケール（1〜2m）の精密な距離測定はハード
  購入待ち。TMOS は「居る/居ない」までで、「どこに居るか」までは追わない。

## 5. 用語集

| 用語 | 一言で | 喩え |
|---|---|---|
| TMOS (STHS34PF80) | 熱で存在を検知するセンサー | 暗闇で感じる暖かさ |
| 焦電 PIR | 動きだけ検知する人感センサー | 玄関灯・トイレの電気 |
| presence | 静止していても出る「存在」値 | 「居る気配」 |
| motion | 動いた時だけ出る「動き」値 | 「動いた瞬間」 |
| I2C | 1本の線で複数機器と会話する規格 | 多人数の内線電話 |
| 読み裂け (torn read) | L/H を別々に読んで値が混ざる事故 | 写真を撮る途中で被写体が動く |
| BDU | 同一読み取り内の一貫性保証 | 1ページ分だけのスナップ保証 |
| PaHUB2 / PCA9548A | I2C を8股に分ける切替スイッチ(mux) | 電話交換機 |
| WHO_AM_I | センサーの身分証番号レジスタ | 名札 |
| ODR | センサーが値を更新する周期 | 写真の連写間隔 |
| 道A / 道B | リモート I2C / firmware ドライバ | 外から覗く / 中に作り込む |
| 在室ゲート | 「居る時だけ喋ってよい」の判定 | 入室許可の門番 |

## 6. 次のフェーズ

この検証の「**presence > 200 なら在室**」という結論は、続く **在室状態マシン**
（presence を時系列で見て「在室／不在／就寝」を状態として持ち、heartbeat の
発話を在室時だけ許可する仕組み）の土台になりました。そちらの実装と運用調整が
次の物語です。

残した宿題:
- **設置環境での再較正**: 今回はノートPC（発熱源）の上で測ったのでノイズ床が
  ±130と広め。StackChan の最終設置位置で測り直す。
- **レンズ向きの固定**: 天井や机を向くと検知できない（無人15分の無反応はこれが
  一因だった）。設置時に人/部屋へ向ける。
- 距離・FOV の定量化、ジェスチャーの実地観察、ToF 購入後の視線追従。
