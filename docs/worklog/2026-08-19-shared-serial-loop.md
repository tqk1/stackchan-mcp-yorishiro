# 2026-08-19 — ドアを閉めた。部屋が同じだった

2日前に「無検査の応答テキストがデバイスを固める」問題を修正した
（`docs/worklog/2026-08-17-unchecked-reply-text.md`）。外部環境で
**同じ症状が再発した**。今度は応答テキストを一切送っていない。

前回の判断が誤りだったので、その訂正から始める。

---

## 1. 再発の報告

- 画面真っ黒・タッチ完全無反応・**自動リブートせず**・電源長押しで復帰
- **前回入れた文字数キャップは正しく動いていた**（利用者が確認済み）
- **だがこのターンで字幕は1文字も送られていない** ＝ キャップは働く機会が無かった
- トリガーは `set_volume(volume=100)`。送信直後からデバイスが一切応答しない
- 15秒後に同じ値で再送、22秒後に接続が切れた

利用者の読み: 「あなたの修正は**応答テキストというドア**を閉じたが、
**ドアそのもの**は閉じていない」。

**結論として、これは正しかった。ただし指していた場所は違った。**

---

## 2. 真因 — 全部が同じ一本の列に並んでいる

firmware の、ツール呼び出しが届く地点にこう書いてある:

```cpp
// Use main thread to call the tool
app.Schedule(...)
```

**すべての MCP ツールが Application メインタスクで実行される**
（`mcp_server.cc:604` → `application.cc:165-259`）。そしてそのタスクは:

- `MAIN_EVENT_CLOCK_TICK` — 画面更新
- `MAIN_EVENT_SEND_AUDIO` — 音声
- **`ReplyResult` → `SendMcpMessage`** — 実行中のツールへの ACK 送信

も処理する。**タスク1本、キュー1本、厳密に順番どおり。**

```
どこか1箇所でブロックする
        │
        ├── 画面更新イベントがその後ろ         →  黒画面
        ├── 同じキュー（+ コーデックは i2c_bus_ を
        │    タッチ FT6336 と共有）            →  タッチ無反応
        ├── ACK も同じキューの後ろ             →  gateway から見て無応答
        └── TWDT にメインタスク未登録
             + CONFIG_ESP_TASK_WDT_PANIC 無効  →  リブートしない
```

**観測4点が、1つの原因から全部出る。**

そして重要なのはここ — **前回の「長すぎる字幕」も同じ場所で止まっていた。**
`set_subtitle` も MCP ツールなので同じタスクで走り、その中で `lv_refr_now()`
を同期実行していた。**入口が違うだけで、詰まった部屋は同じだった。**

前回「実害は gateway 側で塞げる」と判断した。**塞いだのは入口の1つにすぎない。**

---

## 3. なぜ `set_volume` だったのか

**そのターンでフラッシュに書く唯一の呼び出し**だから。

`AudioCodec::SetOutputVolume`（`audio_codec.cc:40-46`）は音量を NVS に保存し、
`Settings` のデストラクタが `nvs_commit()` を**同期実行**する。そして
**値が変わっていなくても無条件に**書いていた。要求は 100、既に 100、それでも
フラッシュへ行く。

正常応答した直前の `set_status_text` は NVS に触れない。時系列と一致する。

---

## 4. クラッシュではないことの確定

`sdkconfig:1568` は `CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=y`、遅延 **0秒**。

⇒ `ESP_ERROR_CHECK` が `abort()` していたなら**リブートするはず**。
リブートしていない ⇒ **クラッシュではなく、どこかで待って止まっている。**

これは推測を1つ潰せる、安上がりで強い判定だった。

---

## 5. ログが証明をやめていた地点

利用者は「id=29/30 に応答が記録されていない ＝ デバイスが無応答」と読んだ。
**gateway のコードはそれを支持しない。**

`esp32_client.py:124-133` は、**成功時もタイムアウト時も何もログに出さない。**

- 「応答が記録されていない」は、**即座に応答していた場合とまったく同じに見える**
- 直前の id=28 が見えたのは**成功したからではなく、失敗したから**
  （`set_status_text` は古いファームで "Unknown tool" になる）

**エラーだけが見えるログは、読む人に「見えているものが全記録だ」と誤読させる。**
利用者は緻密に読んだ上で誤った。結論自体は物理的な証拠（電源を抜いた）で
立っているが、**ログは初めから何も言えなかった。**

### 副産物 — 1週間前の数字が繋がった

利用者は8/17に「`set_volume` は約60秒かかったが動いた」と報告していた。
当時は「ツール呼び出しは往復2回だから」と答えた。**往復2回に60秒はかからない。**

`RESPONSE_TIMEOUT = 10.0`（`esp32_client.py:41`）。
10秒タイムアウト → エージェントが再試行 → タイムアウト → 再試行 → いずれ通る。
**60秒とはそういう形。この不具合は少なくとも当時から断続的に起きていた。**

## 6. 実施した修正

### firmware ①: 値が変わらなければ NVS に書かない

再試行がまさに同じ値を送るので、**当該のブロックが消える。**

### firmware ②: メインループを task watchdog の監視下へ

特定のハングを直すものではなく、**次の未知のハングを生存可能にする**もの。

```cpp
esp_task_wdt_config_t wdt_config = {
    .timeout_ms = MAIN_LOOP_WDT_TIMEOUT_MS,   // 30秒
    .idle_core_mask = 0,
    .trigger_panic = true,
};
esp_task_wdt_reconfigure(&wdt_config);
esp_task_wdt_add(nullptr);
```

**ここに罠が2つあった。**

**(a) `portMAX_DELAY` のまま登録すると、健全な機体を誤リブートする。**
ループは `xEventGroupWaitBits(..., portMAX_DELAY)` で待つ。イベントが来ない
アイドル時 — つまり大半の時間 — **feed されない**。待機に5秒の上限を入れて
定期的に起こす形にした（`bits == 0` は全分岐がビット判定なので素通りする）。

**(b) アイドルタスク監視は外した**（`idle_core_mask = 0`）。sdkconfig は
`CHECK_IDLE_TASK_CPU0/1=y` だが、**panic を有効にした今それを残すと、
重い処理でアイドルが回らないだけで再起動する。** アイドル枯渇は今回の障害とは
別物で、はるかに誤検知しやすい。監視対象はメインループ1本に絞る。

タイムアウト30秒は意図的に緩い。あのループは正当に遅い仕事（描画・NVS・I2C）を
するので、**誤った再起動は遅い応答より悪い。**

### gateway: 応答しないデバイスに、そう言わせる

```
ESP32 did not respond within 10s: method=tools/call id=29 (device may be wedged)
```

あわせて、タイムアウト後に届いた遅延応答が「空の `ESP32 notification:`」として
紛れる件も直した。**遅いデバイスと死んだデバイスは別の診断**なので。

## 8. 用語

| 用語 | 意味 |
|---|---|
| **FreeRTOS タスク** | 組み込みの「スレッド」。優先度を持ち、OS が切り替える |
| **イベントループ** | イベントを待って、来たら処理する無限ループ。**1本なら処理は直列** |
| **`app.Schedule(...)`** | 「この処理をメインタスクの列に並べておいて」という依頼。**その場では実行されない** |
| **NVS** | ESP32 のフラッシュ上の設定保存領域。書き込みはフラッシュ操作なので遅い |
| **`nvs_commit()`** | NVS の変更を確定させる。**同期＝終わるまで戻らない** |
| **TWDT** | Task Watchdog Timer。登録したタスクが一定時間 feed しないと発火する |
| **feed（reset）** | 「まだ生きている」とウォッチドッグに知らせること |
| **panic** | 異常終了。この機体では**バックトレースを出して即リブート**する設定 |

## 9. 教訓

**「入力を検査すれば実害は防げる」は、詰まる場所が共有されていないときだけ
成り立つ。**

前回は入口（応答テキスト）を検査して、それで実害は塞げると判断した。
**同じ部屋への入口は他にいくつもあった** — MCP ツールは全部そこを通る。

**そして、外部の利用者が「同じ症状だ」と言ったとき、機序が違うからと
退けてはいけない。** 名指しされた箇所（`DisplayLockGuard`）は今回の経路上に
無かった。だが**「まだ開いている」という結論は完全に正しかった。**
症状が同一だったのは偶然ではなく、**詰まる場所が同一だったから**である。

もう一つ。**一度「不要」と伝えた作業が、必要になることがある。**
8/8 に「ファームの焼き直しは不要」と伝えた。当時は正しく、今は誤り。
**撤回は早いほうがよい。**
