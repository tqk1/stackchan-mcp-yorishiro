## 1. 全体像

### 1.1 何をしたか（一言で）

これまでのスタックちゃんは **「タップ → 1往復 → 終わり」** でした。
今回、**Hermes（頭脳）が質問（「？」）で返したら、タップなしで自動でもう一度聞き耳を立てる** ようにしました。

```
【Before】                          【After（マルチターン）】
 タップ → 録音 → 返事                タップ → 録音 → 返事「好きな色は？」
 （会話おわり。続けるには再タップ）   → 自動で聞き耳 → 「青」→ 返事「なんで青なの？」
                                    → 自動で聞き耳 → ...（最大4往復・沈黙で終了）
```

ポイントは3つの設計思想です：

1. **割り込まない**（CLAUDE.md 設計原則①）— 常時マイク ON にはしない。**Hermes が質問で締めたときだけ** 聞き耳を立てる。普段の夫婦の会話に勝手に入らない。
2. **firmware を触らない**（gateway だけで完結）— マイコンの書き換え（flash）は時間がかかるので、まず PC 側（gateway）の工夫だけで実現できないか試した。結果、できた。
3. **安全弁を必ず置く** — 暴走（自分の声を拾って無限ループ）しないよう、上限ターン数・沈黙での終了・ミュート時停止などのブレーキを多重に張った。

### 1.2 3つのフェーズの地図

| フェーズ | テーマ | 一言でいうと | 完了日 |
|---|---|---|---|
| **Phase 1** | 継続判定（MVP） | 「？」で終わったら自動で聞き耳を立てる土台＋安全弁 | 2026-06-17 |
| **Phase 2** | 文脈保持 | 同じ会話の間は「さっきの話」を Hermes が覚えている | 2026-06-17 |
| **Phase 3** | 仕上げ | ダッシュボードで ON/OFF＋上限時の親切な字幕 | 2026-06-17 |

### 1.3 全体のデータの流れ（構成図）

```
[スタックちゃん本体 (ESP32 firmware)]
   │  ① タップ → 録音（VADが無音で自動停止）→ 音声を送信
   ▼
[gateway (PC上の Python)]  ← 今回の主役。ほぼ全部ここに実装
   │  ② 音声→文字(STT) → Hermesに問い合わせ → 返事を音声化(TTS)して再生
   │  ③ 返事が「？」で終わる？ → YES なら…
   │      ・少し待つ（ガードスリープ：自分の声を拾わないため）
   │      ・本体に「もう一回聞き耳を立てて」と指示（listen:start 再送）
   ▼
[スタックちゃん本体]
   │  ④ また録音が始まる → ①へ戻る（最大4回まで）
```

この「③で gateway が本体に listen:start を再送する」だけがマルチターンの核心です。
あとは全部、**いつ再送するか／いつ止めるか** の判断と安全弁です。

## 2. 採用した仕組みの解説

### 2.1 継続判定 — 「会話のバトンが渡されたか」を見る

- **何か**: Hermes の返事の末尾が「？」または「？」かどうかで、会話を続けるか決めるルール。
- **なぜ必要か**: 機械が「いつ聞き耳を立て直すか」を判断する基準が要る。常時 ON は原則①違反。「？＝あなたの番だよ」という人間の自然な合図を流用した。
- **喩え**: トランシーバーの「どうぞ」。相手が「どうぞ」と言ったらこちらが話す番、と分かる。Hermes の「？」が「どうぞ」にあたる。
- **使った場面**: 毎ターンの最後で「この返事は？で終わってる？ なら聞き耳を立てよう」と判定。

### 2.2 純関数 `should_continue` — ルールを1か所に集める

- **何か**: 「継続すべきか？」の全条件を1つの関数（`multiturn.py` の `should_continue`）にまとめたもの。状態を持たず、入力だけで答えが決まる（＝**純関数**）。
- **なぜ必要か**: 「？で終わり」「Hermes 経由」「上限未満」「接続中」「非ミュート」「録音中でない」…と条件が多い。あちこちに `if` を散らすとバグの温床。1か所に集めればテストも書きやすい。
- **喩え**: 自動販売機の「買える条件チェック」。お金が足りて・在庫があって・売り切れでない…を1か所で判定し、YES/NO だけ返す。
- **使った場面**: `hermes_bridge.py` の `_maybe_continue` が、毎ターンこの関数に状態を渡して YES/NO をもらう。

```python
# multiturn.py（要点。引数を全部もらい、bool を返すだけ＝テストしやすい）
def should_continue(*, enabled, route, reply, turn_count, max_turns,
                    device_connected, muted, recording) -> bool:
    return (enabled and route == "hermes"
            and reply_invites_continuation(reply)   # 末尾が ？/？
            and turn_count < max_turns               # 上限未満
            and device_connected and not muted and not recording)
```

### 2.3 VAD（無音自動停止）— 録音は本体が勝手に止める

- **何か (VAD = Voice Activity Detection)**: 「人が喋っているか」を本体（firmware）が判定し、**喋り終えて一定時間 無音なら録音を自動で止める** 仕組み。
- **なぜ必要か**: gateway が「もう一回聞いて」と指示しても、いつ録音を止めるかが決まっていないと困る。実は firmware に既に VAD があり、**gateway が再送した listen でも同じように効く** ことが調査で分かった（これが「firmware 改修不要」の決め手）。
- **喩え**: 留守番電話。喋り終えて静かになると勝手に録音が切れる。あれと同じ。
- **使った場面**: `firmware/.../stackchan.cc` の `PollTouchpad()`。warmup 800ms → 発話検知 → 発話後 1200ms 無音で停止（無発話なら 30 秒で打ち切り）。

> **教訓**: 「機能が無い」と思い込む前に、実機で動いているコードを読む。当初メモには「firmware に VAD 自停止コード無し」とあったが**誤り**で、既に存在していた。この事実確認だけで「firmware を flash する」という重い作業がまるごと不要になった。

### 2.4 ガードスリープ — 自分の声を拾わないための「間」

- **何か**: 聞き耳を立て直す前に、固定時間（既定 1000ms）だけ待つ処理。
- **なぜ必要か**: このスタックちゃんは **AEC（エコー除去）が OFF**。再生中の自分の声をマイクが拾うと、それを「ユーザー発話」と誤認して無限ループしかねない。TTS 再生の最後の余韻が消えるまで待ってから聞き耳を立てる。
- **喩え**: 自分の声が反響する部屋で会話するとき、「言い終わってから一拍おいて」相手に耳を傾ける、あの一拍。
- **使った場面**: `_maybe_continue` で `send_listen_state("start")` の直前に `asyncio.sleep(guard_ms/1000)`。環境変数 `MULTITURN_TTS_GUARD_MS` で実機調整可能。

### 2.5 会話セッション id とローテーション（Phase 2）— 「今この会話」を区切る

- **何か**: Hermes に送る会話 id を、**固定** から **会話ごとに使い捨て** へ変えた仕組み。
- **なぜ必要か**: Hermes は「同じ session id ＝同じ会話」として文脈を覚える。固定 id だと **何日分もの会話が1つの袋に溜まり続け**、古い話題のゴミが混ざる。会話ごとに id を変えれば「今の会話」だけがきれいに繋がる。
- **喩え**: ノートの新しいページ。会話を始めるたびに新しいページを開き、しばらく書かなければ次は別のページから。前のページ（前の会話）は残るが混ざらない。
- **使った場面**: `conversation_id()` が「最後の発話から 180 秒以内なら同じ id を再利用、超えたら新 id を発行」。`HERMES_SESSION_WINDOW_S=0` にすると旧来の固定 id に戻せる（逃げ道を1ノブで用意）。

```python
# 例: stackchan-voice-1fb22a2c  （base 名前空間 + 使い捨ての短いID）
```

### 2.6 永続トグル vs 環境変数（Phase 3）— 「設定の主導権は誰が持つか」

- **何か**: マルチターンの ON/OFF を、**ダッシュボードのトグル（ファイルに保存＝永続）** で切り替えられるようにした。
- **なぜ必要か**: それまでは環境変数 `STACKCHAN_MULTITURN=1`（systemd の設定ファイル）でしか切り替えられず、毎回サーバ設定を編集＋再起動が必要だった。ダッシュボードのスイッチで切れると楽。
- **喩え**: 壁のスイッチ（永続トグル）と、ブレーカー（環境変数）。普段は壁のスイッチで操作したい。ブレーカーが常に優先だと壁のスイッチが無意味になる。
- **使った場面**: `control.multiturn_enabled()` が実行時の唯一の判断基準。環境変数は「設定ファイルにまだ値が無いときの初期値」だけに格下げした（→ 詳細は章4と事件簿3）。

## 4. 設計判断の記録

### 4.1 gateway だけで作る vs firmware も改修する（二段方式）

| 案 | 速さ | リスク | 採否 |
|---|---|---|---|
| **gateway だけ（MVP）** | flash 不要で即試せる | AEC off ＝自己拾音のリスク | ✅ まずこれ |
| firmware continuation | キュー管理で自己拾音を根絶 | ビルド＋flash が重い | 保険（Phase 4・条件付き） |

考え方: **安く出して実機で測り、データで firmware 改修の要否を決める**。実機 E2E で自己拾音ゼロだったので、Phase 4 は不要のまま据え置き。

### 4.2 環境変数と「OR」する vs 永続トグルが勝つ（Phase 3 の肝）

当初メモには「env と永続トグルを **OR**（どちらかが ON なら ON）」と書いてあったが**不採用**にした。

| 案 | 挙動 | 問題 |
|---|---|---|
| env OR トグル | env=1 なら常に ON | 本番は env=1 固定なので、**ダッシュボードで OFF にできない**（トグルが無意味） |
| **永続トグルが唯一の真実**（env は初期値だけ） | トグルの値が常に優先 | ✅ ダッシュボード OFF が env=1 に勝つ＝直感的 |

採用案では `STACKCHAN_MULTITURN` は「設定ファイルにまだ `multiturn` キーが無いときの初期値を決める」だけ。一度トグルを触れば、その値がファイルに保存されて以後はそちらが勝つ。既存デプロイ（env=1）は初回 ON のまま壊れない。

### 4.3 2つのタイムアウトを分離（60秒 と 180秒）

| 用途 | 環境変数 | 既定 |
|---|---|---|
| 継続の打ち切り・上限リセット・heartbeat 抑止の自己失効 | `MULTITURN_SESSION_TIMEOUT_S` | 60 |
| 会話文脈ウィンドウ（Hermes session id ローテ） | `HERMES_SESSION_WINDOW_S` | 180 |

60〜180 秒の間ギャップでは「自動継続ループはもう終わっているが、もう一度タップすれば文脈は地続き」という自然な振る舞いになる。

### 4.4 やらなかったこと（意図的に）

- **常時マイク ON（VAD 常時起動）**: 原則①違反。明示トリガー（タップ／背面なで）のみ。
- **継続ターンだけ listen タイムアウトを短縮**: firmware 側の値なので flash が要る → Phase 4 領域として見送り。
- **Hermes 本体の改造**: 原則④。文脈保持は「送る session id を変える」だけで実現し、頭脳側は触っていない。

## 5. つまずきの事件簿

### 事件簿1: ガードは返事の長さに比例させるべき？

- **症状**: プランでは「`sleep(返事の再生時間 + マージン)` だけ待つ」としていた。長い返事ほど長く待つ設計。
- **調査**: `tts/orchestrator.py` を読むと、音声フレームは**実時間ペースで送出**（1フレーム=20ms）。つまり再生が終わるころには送出も終わっており、本体に残るのは「デコード待ち行列の余り（最大 ~0.8秒）」だけ。
- **原因**: 「返事の長さ」は既に再生の進行で吸収されている。比例させるのは過剰。
- **修正**: ガードを **固定 1000ms** に。返事の長さに依存させない。
- **教訓**:

> **教訓**: 「とりあえず長めに待つ」は安全に見えて、根拠を読むと過剰だったりする。ペーシングの実装を1か所読めば、待つべきは「行列の余り」だけと分かった。**待ち時間は勘でなく、データの流れから逆算する**。

### 事件簿2: 「覚えてる！」は文脈保持の成功？ それとも漏れ？

- **症状**: Phase 2 の文脈テストで、別会話（新しい session id）にしたのに Hermes が「ミドリガメ」の話を覚えていた。文脈が漏れている＝**分離 FAIL** に見えた。
- **調査**: 何を覚えていて何を忘れるかを観察。「ケンジ」は Hermes が**元々知っている owner 名**。「ミドリガメ」は「**覚えておいて**」と頼んでいた。
- **原因**: 「覚えておいて」は Hermes の **write_note ツール**を発火させ、notes に**永続保存**していた。これは session を跨ぐ長期記憶＝**設計どおり**で、session 文脈の漏れではなかった。
- **修正**: メモ化されない、ただの言い捨て（passing-mention の nonce ワード）で再テスト → 別 session では「履歴に無い」と正しく分離。
- **教訓**:

> **教訓**: テストの素材が「別の仕組み」を巻き込むと、誤った結論に着地する。「覚えて」という指示は long-term memory（notes）を起動するので、session スコープのテストには不適。**切り分けたい層だけを刺激する素材を選ぶ**。

### 事件簿3: env と OR したらトグルが効かない

- **症状**: Phase 3 で「env か永続トグルのどちらかが ON なら ON」（OR）にしようとした。
- **調査**: 本番は systemd の設定で `STACKCHAN_MULTITURN=1` が常にセットされている。OR だと env=1 が常に勝つ。
- **原因**: OR では **ダッシュボードのトグルを OFF にしても env=1 が勝って ON のまま**＝トグルが無意味。
- **修正**: 「永続トグルが実行時の唯一の真実、env は初期値だけ」に設計変更（4.2）。
- **教訓**:

> **教訓**: 「両方見て OR」は柔軟そうで、実は**主導権が曖昧**になる。ユーザー操作（トグル）と環境設定（env）が衝突したらどちらが勝つか、最初に1つ決める。ここでは「人が触った方が勝つ」を採用した。

### 事件簿4: ライブ設定を読むテストが、将来トグルすると壊れる

- **症状**: 継続ゲートを「永続トグル読み取り」に変えた結果、テストが本物の設定ファイル（`~/.stackchan/control_state.json`）を読むようになった。ユーザーがダッシュボードでトグルを書き込むと、テストがその値を拾って壊れる懸念。
- **原因**: 本番兼開発機なので、テストとライブ状態が同じファイルを見てしまう。
- **修正**: テストのヘルパー（`_patch_voice_pipeline`）で `control.multiturn_enabled` を**環境変数リーダーに差し替え**、テストはライブファイルに依存しないようにした（既存の `routing_force_hermes` と同じ手口）。
- **教訓**:

> **教訓**: テストは「外の世界の状態」に依存させない。本番と同じマシンで動かすなら特に。設定の読み口をテスト時だけ差し替えられる構造にしておくと、ライブ状態に振り回されない。

### 7.3 質問例（コピペでそのまま Claude / Gemini に貼れます）

**概念系**
- 「VAD（音声区間検出）とは何ですか？ なぜマルチターン会話に必要なのか、留守番電話の喩えを使って詳しく説明してください」
- 「AEC（音響エコーキャンセル）とは何ですか？ これが OFF だと『自己拾音で無限ループ』する理由を初心者向けに教えてください」
- 「『純関数』とは何ですか？ `should_continue` が純関数だとテストが書きやすい理由を具体例で説明してください」

**コード系**
- 「この `should_continue` 関数の各条件（route=='hermes'、turn_count<max_turns など）が、それぞれどんな暴走を防いでいるのか1つずつ説明してください」
- 「`_maybe_continue` の中で `asyncio.sleep(guard_ms/1000)` を `send_listen_state` の前に置く理由は？ 後ろに置くとどうなりますか？」
- 「`conversation_id()` が『180秒以内なら同じ id、超えたら新 id』を返す実装は、どう書けば良いですか？ Python の例で示してください」

**仕組み系**
- 「gateway が本体に listen:start を再送すると、firmware の VAD 状態がリセットされて『また自動で録音が止まる』という流れを、ステップごとに説明してください」
- 「`MULTITURN_SESSION_TIMEOUT_S`(60秒) と `HERMES_SESSION_WINDOW_S`(180秒) を別々のタイムアウトにすると、60〜180秒の間にタップしたらどう振る舞いますか？」
- 「ダッシュボードのトグルを押すと `POST /control/multiturn` → gateway → 設定ファイル保存、と流れるのを、HTTP の観点で順に説明してください」

**設計系**
- 「マルチターンの ON/OFF で『環境変数と永続トグルを OR する』案がなぜ却下されたのか、トレードオフを整理して教えてください。他にどんな選択肢がありましたか？」
- 「『firmware を改修せず gateway だけで実装する』判断のメリットとデメリットは？ どういう実機データが出たら firmware 改修に踏み切るべきですか？」
- 「『Hermes 本体を改造せず、送る session id を変えるだけで文脈保持を実現する』という方針の利点は？ なぜ頭脳側を触らない方が良いのですか？」
