## 0. 何が起きて、何を作ったか（30秒まとめ）

スタックちゃんは、人に言われなくても**自分で勝手に動く**ことがある — 朝に天気を読み上げたり、帰宅を察して「おかえり」と言ったり、在室／不在の判断を切り替えたり、家電を操作したり。ところが「いつ・何を・どんな結果でやったか」が**どこにも構造化されて残っていなかった**（ログの流れに一瞬出て消えるだけ）。

そこで、こうした自律行動を1件1行で書き溜める**専用の記録帳（JSONL ファイル）**を新設し、各行動の発生地点に「ここを通ったら1行書け」という計装を仕込んだ。そして、その記録帳と日次レポートをまとめて新しい順に返す窓口（`/control/activity`）を作り、ダッシュボードに「📜 フィード」タブとして見えるようにした。

ついでに、直近のセンサー改修（静止在室・就寝ラッチ）に**表示が追いついていなかったセンサータブ**を追従させた。

途中、計装が**既存のテストを巻き込んで本物の記録帳を汚す**バグを踏み、テストの隔離で直した（事件簿1）。最後にケンジさんの要望で、毎時の cron（CC使用率）はフィードから外した。

## 1. 全体像

### 1.1 登場人物（システム構成）

```
[スタックちゃんの自律行動たち]
  heartbeat(天気/メモ発話・仕草)
  proactive(おかえり等の自発あいさつ)
  presence(在室判定の切り替わり)
  switchbot(家電操作)
        │  どれも「やった瞬間」に activity_log.append() を呼ぶ
        ▼
  ~/.stackchan/activity_log.jsonl   ← 1行1イベントの記録帳（新設）
        │  read_recent() で新しい順に読む
        ▼
[gateway] GET /control/activity ──+ 日次レポート(presence_reports/*.json)も合流
        │   ts_unix(時刻)で降順に並べてまとめて返す
        ▼
[status-api :8080] 中継役（許可リストに /control/activity を追加）
        ▼
[dashboard.html] 📜 フィードタブ（開いた時 + 🔄ボタンで取得）
```

ポイントは2つ。**(A)** 書く側（自律行動）と読む側（フィード）を1枚の記録帳で疎結合にしたこと。**(B)** 記録帳には無いもの（日次レポート）は、読む瞬間に別の引き出しから合流させたこと。

### 1.2 今回の一番大事な設計判断（先に結論）

**「記録は前向き（これから）に貯める JSONL 方式」** を選んだ。過去ログ（journald）を後から解析する案もあったが、文言依存で壊れやすく保存期間で消える。詳しくは4章。

## 2. 採用した技術・考え方の解説

### 2.1 JSONL — 「レシートを1枚ずつ箱に放り込む記録帳」

- **何か**: 1行 = 1件の JSON（データのかたまり）が縦に並んだテキストファイル。`JSON Lines` の略。
- **なぜ必要か**: 自律行動は「いつ・何を・結果は」を後から時系列で振り返りたい。表計算のように行を足していける形が一番素直。
- **喩え**: 買い物のたびに**レシートを1枚ずつ箱に放り込む**イメージ。箱（ファイル）の末尾に足すだけなので速いし、途中で電源が落ちても、それまでのレシートは無事。
- **使った場面**: `~/.stackchan/activity_log.jsonl`。1行はこんな形：

```json
{"ts_unix": 1782549332.9, "source": "proactive", "kind": "speak", "status": "ok", "subtype": "absent_active", "text": "おかえり"}
```

`source`（誰が）/`kind`（何を）/`status`（結果）/`text`（中身）/`ts_unix`（いつ＝1970年起点の秒数）。この素朴さが、後で読む側を楽にする。

### 2.2 fire-and-forget（撃ちっぱなし）— 「記録係がコケても本番の劇は止めない」

- **何か**: 記録の書き込みが失敗しても、エラーを上に投げず、警告だけ出して握りつぶす方針。
- **なぜ必要か**: 「おかえり」と喋る処理の**おまけ**で記録を書く。もし記録の失敗で発話まで巻き添えに止まったら本末転倒。
- **喩え**: 舞台の**記録係がペンを落としても、役者は芝居を続ける**。記録はあくまで脇役。
- **使った場面**: `activity_log.append()` の中で `try/except` し、ディスクエラーや変換エラーを WARNING ログだけにして本線へ伝播させない。既存の `event_log.py`（ファーム由来イベントの記録）と同じ流儀を踏襲した。

### 2.3 リスナー登録（購読）— 「町内放送に複数の人が耳を傾ける」

- **何か**: 「在室状態が変わった」という出来事に対して、興味のある関数を**事前に登録**しておき、出来事が起きたら全員に通知する仕組み（オブザーバーパターン）。
- **なぜ必要か**: 在室の切り替わりは、すでに proactive（あいさつ判断）が聞き耳を立てていた。そこに「記録もする」を**追加**したいが、お互いを知らないまま並べたい。
- **喩え**: **町内放送（在室が変わったよ！）に、複数の家がそれぞれ耳を傾ける**。放送する側は誰が聞いているか気にしない。
- **使った場面**: `presence.register_on_state_change(...)`。調べてみると、この仕組みは**すでに複数登録に対応していた**（内部はリスト）。なので proactive の隣に、記録用の関数 `_record_presence_transition` を1行登録するだけで済んだ（→ 事前の計画では「単一登録だから複数化が必要」と読んでいたが、実物を見たら不要だった）。

### 2.4 読み込み時マージ — 「複数の引き出しから紙を集めて日付順に並べる」

- **何か**: 複数のデータ源を、**読む瞬間に**1つに合体させて返すやり方。
- **なぜ必要か**: フィードには「記録帳（JSONL）の行」と「日次レポートのリンク」を混ぜて出したい。でも両者は別物・別保管。事前に1ファイルへ統合すると二重管理になる。
- **喩え**: 質問されてから、**机の引き出しA（記録帳）と引き出しB（日次レポート一覧）から紙を集め、日付順に並べて手渡す**。普段は別々にしまっておく。
- **使った場面**: `_gather_activity()` が `activity_log.read_recent()` と `_list_presence_reports()` を呼び、`ts_unix` で降順ソートして上位 N 件を返す。重い読み込みは `asyncio.to_thread`（別スレッド）に逃がし、本線（会話や WebSocket）を待たせない。

### 2.5 計装は「チョークポイント（必ず通る改札）」に置く

- **何か**: 記録を仕込む場所を、**その行動が必ず1回通る1点**に絞ること。
- **なぜ必要か**: あちこちに `append()` を撒くと、書き漏れ・二重記録が起きる。
- **喩え**: 駅の人数を数えるなら、**全員が必ず通る改札にカウンターを1つ置く**。出口ごとに数えると数え間違える。
- **使った場面**: 家電操作は `switchbot.send_command` を呼び出す**ディスパッチの1点**（`stdio_server.py`）に置いた。発話は heartbeat / proactive それぞれの「実際に喋り終えた直後」。在室は町内放送（2.3）。

### 3.1 計装のしかた（発話の例）

「天気とメモ、どちらを喋ったか」を記録に残したいが、元コードは `天気 or メモ` を1行で書いていて、どちらが採用されたか分からなくなっていた。そこで分岐を開いて種別（subtype）を持たせ、喋り終えた直後に記録した：

```python
line = await self._check_weather()
subtype = "weather"
if not line:
    line = await self._check_memo()
    subtype = "memo"
if not line:
    return False
started = self._monotonic()
await self._perform_speak(line)          # ← 実際に喋る
activity_log.append("heartbeat", "speak", subtype=subtype,
                    text=line, duration_ms=int((self._monotonic()-started)*1000))
```

`duration_ms`（喋るのにかかったミリ秒）も一緒に残しておくと、後で「やけに長い発話」を見つけやすい。

### 3.2 センサータブの追従（表示の盲点を埋める）

`/control/presence`（在室状態を返す窓口）は、直近の改修で既に **`asleep`（就寝ラッチ）** と **`occupancy`（静止在室の内部値）** を返していた。ところがダッシュボードはそれを**表示していなかった** — データは来ているのに画面に出ていない、いわば「届いた荷物を開けていない」状態。これを在室判定セクションに2行足して解消した。あわせて不在猶予スライダーの上限を `600 → 1200` 秒に広げた（就寝ラッチ運用で 1080 秒を使う実績があり、推奨値が 600 を超えても画面から設定できるように）。

> **教訓**: 「APIは値を返しているのに画面に出ない」は、バックエンドとフロントの**改修タイミングのズレ**で起きやすい。新しいフィールドを足したら、それを映す側（ダッシュボード）まで1セットで追うこと。

## 事件簿1: テストを走らせたら、本物の記録帳が勝手に汚れた

**症状**: 実装が一段落して `~/.stackchan/` を覗くと、見覚えのない `activity_log.jsonl` が出来ていて、中に `おかえり` `おはよう` `おやすみ` が並び、`AABBCCDDEEFF`（明らかにダミーの機器ID）への家電操作まで記録されていた。本番のスタックちゃんは喋っていないのに。

**調査**: タイムスタンプは作業中の時刻。中身は**テスト用の文言ばかり**。`grep` で追うと、これらは `test_proactive.py` や `test_switchbot.py`（既存テスト）が使うダミーデータだった。

**原因**: 今回 proactive や switchbot の「実際に動く地点」に `activity_log.append()` を仕込んだ。すると、**それらの地点を通る既存テスト**が走るたびに記録が書かれる。テストは記録帳のパスを指定していないので、`append()` は**既定パス＝本物の `~/.stackchan/activity_log.jsonl`** に書いてしまっていた。本番の旧コードはこのファイルを作らないので、中身は100%テスト由来と断定できた。

**修正**: テスト全体で記録帳の保存先を**使い捨ての一時フォルダ**に強制的に向ける「autouse フィクスチャ」を `conftest.py`（テスト共通設定）に1つ追加した：

```python
@pytest.fixture(autouse=True)
def _isolate_activity_log(monkeypatch, tmp_path):
    monkeypatch.setenv("STACKCHAN_ACTIVITY_LOG", str(tmp_path / "activity_log.jsonl"))
```

`autouse=True` は「全テストに自動で適用」、`tmp_path` は「テストごとに使い捨ての作業フォルダ」。これで、どのテストが記録を書いても本物の家計簿には触れない。汚れた本物のファイルは削除した。

> **教訓**: **既定パスにファイルを書く副作用を持つ部品**は、テストで一括隔離するのが鉄則。1個ずつのテストで気をつけるのではなく、`conftest.py` に「全テスト共通の使い捨て作業机」を用意して、本物の環境（ホームディレクトリ）を絶対に触らせない。喩えるなら、**実験は必ず使い捨てのトレーの上でやり、本物の調理台を汚さない**。

## 4. 設計判断の記録

### 4.1 記録方式: 前向き JSONL ✅ / 過去ログ解析 / 両方

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| **前向き JSONL** ✅ | これから起きる行動を1行ずつ貯める | 構造化・堅牢・既存 `event_log` と同型 | 実装日より前は記録が無い |
| 過去ログ解析 | journald を後から `grep` | 過去分も拾える | ログ文言に依存し壊れやすい・保存期間で消える |
| 両方 | 過去をバックフィル＋前向き | 履歴も将来も揃う | 実装コスト最大 |

**前向き JSONL を採用**。フィードは「これからの振り返り」が主目的で、過去の発話は journald にしか無くても困らない。壊れにくさと素直さを優先した。

### 4.2 cron（CC使用率）: いったん載せて → 外した

最初は要望どおり毎時の CC使用率（cron）も載せた。だが実機で見ると、**毎時1件の cron がフィードを占有**し、肝心の自律行動が埋もれた。しかも CC使用率は**サーバータブで既に見えている**（重複）。そこでケンジさん判断で cron をフィードから**完全除外**（バックエンドの合流・UIのフィルタ・cron用テストを削除）。フィードは「スタックちゃんが自律的にやったこと＋日次レポート」に純化した。

> **教訓**: 「載せられる」と「載せるべき」は別。情報量より、**埋もれさせない**ことが一覧の価値を決める。実機で見て初めて分かる過密もある。

### 4.3 フィルタはクライアント側

タブ上部の「自律/家電/在室」フィルタは、サーバーに毎回問い合わせず**取得済みのデータを画面側で絞る**だけにした。イベント数が少ないので、全部取ってから手元で選り分ける方が速くて単純（サーバー往復が減る）。

### やらなかったこと（意図的に）

- **連続ポーリングしない**: フィードはまれにしか増えないので、開いた時と🔄ボタンの時だけ取得。電池と通信の無駄を避ける。
- **生のレポートファイルを配信しない**: 日次レポート項目は「▶診断タブで見る」へ誘導。すでにある診断タブを使い回し、新しいファイル配信口を増やさない。
- **presence の複数リスナー化をしない**: 既に対応済みだったので手を入れない（2.3）。

## 5. 用語集

| 用語 | 一言で | 喩え |
|---|---|---|
| JSONL | 1行1件の JSON が並ぶファイル | レシートを1枚ずつ箱に放り込む |
| append（追記） | ファイル末尾に1行足す | ノートの最後の行に書き足す |
| ローテーション/保持期間 | 古い行を間引く（14日） | 古いレシートは2週間で処分 |
| fire-and-forget | 失敗しても本線を止めない | 記録係がコケても芝居は続く |
| リスナー登録/購読 | 出来事を聞き耳を立てて受け取る | 町内放送に複数の家が耳を傾ける |
| チョークポイント | 必ず1回通る計装地点 | 駅の改札にカウンター1つ |
| 読み込み時マージ | 読む瞬間に複数源を合体 | 引き出しA・Bから紙を集めて日付順に |
| autouse フィクスチャ | 全テスト共通の自動下準備 | 実験前に使い捨てトレーを必ず敷く |
| `ts_unix` | 1970年起点の秒数で表す時刻 | 世界共通の「通し番号の時計」 |
| エンドポイント | HTTP の呼び出し窓口 | 受付カウンターのひとつ |
| 許可リスト（allowlist） | 中継を通す URL の白名簿 | 通してよい人の名簿 |
