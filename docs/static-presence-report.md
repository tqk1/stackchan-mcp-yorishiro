## 0. 何が起きて、何を作ったか（30秒まとめ）

「センサーの 1m 前に座っているのに、在室と認識されない」という症状。原因は、使っているセンサーが**「動くもの」には反応するが「じっと座っている人」を約1分で見失う**性質を持っていたこと。

そこで、センサーが内部で捨てていた**生の温度信号**を在室判定に加え、「いつもの空っぽの部屋」との**差**で静止した人を見つけるようにした。途中、9.7日分の実ログで検証したら**「2.6日間ずっと在室と言い続ける」重大バグ**が見つかり、設計を作り直した。最終的に実機で、9分間じっと座っても在室を保ち、席を立てば即座に解除されることを確認した。

## 1. 全体像

### 1.1 登場人物（システム構成）

```
[StackChan 本体(ESP32) + TMOSセンサー]   ← 熱で人を感じるセンサー
        │  I2C(機械同士の短距離通信)
        ▼
[gateway (Python・このリポジトリ)]
        │  presence.py が5秒ごとにセンサーを読む
        ▼
   在室状態(active / absent / quiet / unknown)を決める
        │
        ├─→ heartbeat(自発的な仕草・発話)を「人がいる時だけ」許可
        └─→ /control/presence (ダッシュボードや確認用のHTTP窓口)
```

今回いじったのは **gateway の `presence.py`** だけ。センサー本体（ファームウェア）の焼き直しは不要だった。

### 1.2 今回の一番大事な設計判断（先に結論）

**「センサーが出してくる『加工済みの人感値』だけを信じるのをやめ、『生の温度値』を併用する」** こと。理由は2章・4章で順を追って説明する。

## 2. 採用した技術・考え方の解説

ここは「何か → なぜ必要か → 喩え → 今回どこで使ったか」の4点セットで説明する。

### 2.1 TMOSセンサーの2つの値 — 「番犬」と「温度計」

- **何か**: 今回のセンサー（STHS34PF80、熱で人を感じる「熱式センサー」）は、主に2種類の数値を返す。`presence`（人感値）と `object_raw`（生の温度信号）。
- **なぜ必要か（の前に、性質の違いが今回の核心）**:
  - `presence` は、センサーが内部の賢いアルゴリズムで「**動きのある熱源**」を強調して出す値。動くと大きく、止まると約1分でスーッと0付近に戻る。
  - `object_raw` は、**生のサーモパイル（熱を電気に変える素子）の読み**。止まっている人の暖かさも淡々と拾い続ける。
- **喩え**:
  - `presence` =「**動くものにだけ吠える番犬**」。侵入者が動けば吠えるが、じっと座られると「もう敵じゃない」と静かになる。
  - `object_raw` =「**部屋の温度を淡々と記録し続ける温度計**」。動こうが止まろうが、暖かいものがあれば数値に出る。
- **今回どこで使ったか**: 従来は番犬（`presence`）の声だけで在室判定していた。だから座って動かない人を見失った。今回は温度計（`object_raw`）の値も判定に足した。

> **教訓**: センサーが親切に「加工済みの便利な値」をくれても、その加工が自分の用途（静止した人の検知）に合っているとは限らない。**生データに何が残っているかを必ず見る。** 今回は生データに答えが残っていた。

### 2.2 適応ベースライン（背景差分）— 「間違い探し」

- **何か**: 「人がいない時のいつもの値」を基準（ベースライン）として常に推定し続け、**今の値がその基準をどれだけ上回ったか**で人を検出する手法。画像処理などで「背景差分」と呼ばれる古典的なやり方。
- **なぜ必要か**: `object_raw` は「人がいるか」だけでなく「**部屋の温度（室温）**」でも上下してしまう。実測中、室温が 30.9℃ → 32.3℃ に上がるだけで、空室の `object_raw` が約 -650 もズレた。だから「○○以下なら在室」と**固定の線引きはできない**。「いつもの空室の値」を動く基準として持ち、その**差**を見るしかない。
- **喩え**: **間違い探し**。「いつもの空っぽの部屋の絵」を覚えておき、今の絵と見比べて「ここだけ違う（暖かい）」を人だと判断する。背景（壁や床）の色が季節で多少変わっても、覚えている絵の方も更新すれば、差だけはちゃんと取れる。
- **今回どこで使ったか**: `object_raw − ベースライン > マージン(150)` を「静止した人がいる」サインとした。

### 2.3 アーミング（武装）— 「物音を確認してから構える用心棒」

- **何か**: 「静止検知」を有効にする前に、**一度は本物の『動き』を確認する**というゲート（門番）。動きを確認したら arm（武装＝構える）状態になり、その時だけ温度差を在室と見なす。
- **なぜ必要か**: 温度差だけで在室と判定すると、**日差しで温まった壁**や**動かない家電**を「人」と誤検知してしまう。これらは「動き」を伴わない。だから「まず動きを見てから」という条件を付ける。
- **喩え**: **用心棒**。ただ暖かいだけのストーブには反応しない。「コトッ」という物音（動き）を一度聞いてから初めて「誰か来たな」と身構える。
- **今回どこで使ったか**: `moving`（番犬が吠えた）を見て初めて `armed=True`。実機E2Eでは、人が近づいて温度差が +186 出ても、まだ動きを確認できていない瞬間は**あえて検知しなかった**（＝壁の誤検知防止が効いている証拠）。

### 2.4 非対称EMA — 「見送りはサッと、なじみはゆっくり」

- **何か**: ベースライン（いつもの空室値）を少しずつ更新していく平滑化のやり方。ただし**値が下がる時は速く、上がる時は遅く**更新する（＝非対称）。EMAは「指数移動平均」、つまり「最近の値を重めに、昔の値を薄めに混ぜていく」平均。
- **なぜ必要か**: 4章の事件簿で詳しく書くが、「人がいる間は基準を固定（凍結）」という素直な案が**重大バグ**を生んだ。代わりに「常に更新、ただし速さを上下で変える」ことで、(a) 人が出ていったら基準を**サッと**下げて即座に『不在』を検知でき、(b) 人が来てもゆっくりしか馴染まないので**静止した人を保持**でき、(c) 万一おかしな高い値が続いても、ゆっくりとはいえ最後は吸収されるので**永久に張り付かない**。
- **喩え**: **お客さんの扱い**。来てもすぐには「常連（＝基準）」扱いしない（ゆっくり馴染む＝人を保持）。でも帰ったらサッと席を片付ける（速く下げる＝離脱を即検知）。
- **今回どこで使ったか**: ベースライン更新の係数を、下げ方向 `0.08`（速い・約60秒で馴染む）／上げ方向 `0.004`（遅い・約40分）に分けた。

## 3. 工程の流れ（時系列）

### 3.1 症状の実測 — まず「今の数値」を取る

ユーザーが1m前に座っている状態で、センサーの現在値を取得した。

| 取得値 | 結果 | 意味 |
|---|---|---|
| `presence` | -10（≒0） | 番犬は静止した人を見失っている |
| `object_raw` | -8060 | 温度計はちゃんと人を捉えている |
| `last_seen_s_ago` | 873.9秒 | 14分半「未検知」のまま |

→ 18分のデバウンス（猶予時間。後述）だけで辛うじて在室を保っており、あと3分で「目の前にいるのに不在」になる寸前だった。**症状を数値で確定**できた。

> **教訓**: バグ報告を受けたら、推測より先に「今まさに起きている現象の生数値」を取りに行く。ユーザーが現場（1m前）にいる今しか取れない貴重なデータだった。

### 3.2 空間マッピング — 行き当たりばったりを避ける

「1m前」だけ直しても、他の場所はどうなのか分からない。そこでユーザーが部屋の各地点に約35秒ずつ静止し、全センサー値を連続記録 → 地点ごとに分布を比較した。

**結果（同じ室温での空室値からの `object_raw` 超過量 Δ）:**

| 地点 | Δ(空室との差) | 静止しても検知できるか |
|---|---|---|
| 自分の席 1m（本命） | **+745** | ◎ 余裕 |
| 恵梨子さん席（テーブル） | +290 | ○ |
| 立ち | +260 | ○ |
| キッチン | +134 | △ 弱い |
| ソファ | +29 | ✗ ほぼ死角 |
| 空室（基準） | 0 | — |

空室のノイズは ±35 程度。Δが100以上あれば余裕で見分けられる。**本命の1m席は+745と圧倒的**で、確実に直せると分かった。一方ソファは死角（センサーの視野・距離の限界。部屋スケールは元々ToFセンサー待ちの領域）。

この計測で同時に分かった重要事実: **室温が上がると空室の `object_raw` も連動して動く** → 固定しきい値は不可、適応ベースライン（2.2）が必須、と**実データで確定**した。

### 3.3 設計と実装

`presence.py` に `_update_occupancy()` という判定関数を新設し、占有判定をここに集約した。考え方はシンプル:

```
在室 = 動いている (従来の番犬)  または  (武装中 かつ 温度差がマージン超え)
```

コードの要点（全文は `presence.py` 参照）:

```python
moving = bool(snap.get("present"))          # 番犬の声（従来の検知）
obj = snap.get("object_raw")                # 温度計の生値
if self._obj_baseline is None:
    self._obj_baseline = obj                # 初回は今の値を基準に
if moving:
    self._obj_armed = True                  # 動きを見たら武装
excess = obj - self._obj_baseline           # いつもの空室からの超過
static_present = self._obj_armed and excess > OBJ_PRESENT_MARGIN
occupied = moving or static_present
```

### 3.4 検証（pytest）

判定ロジックは「センサーの読み」を差し替えれば机上でテストできる。9ケース追加（初回起動・武装してからの静止保持・離脱・空室追従・壁は非ラッチ・**長時間静止は最後に解除＝反ラッチ** など）。`pytest 1071 passed`。

## 4. 設計判断の記録（と、事件簿）

### 4.1 事件簿1: 「2.6日間ずっと在室」事件

**症状**: 最初の設計では「**人がいる間はベースラインを凍結**（固定）する」ことにしていた。理由は「更新し続けると、静止した人の暖かさを基準が吸収してしまい、結局その人を見失う」と考えたから。一見もっともらしい。

実装を終えて pytest も緑になった。だが本番投入の前に、**9.7日分の実在室ログ（16万サンプル）に新ロジックを当てて再生（replay）してみた。**

**調査**: replay の結果がおかしかった。

| 指標 | 凍結案 |
|---|---|
| 「静止在室」と判定した時間の割合 | **53%**（多すぎる） |
| 最長の連続在室 | **3700分 = 2.6日** 🔴 |

2.6日間ぶっ通しで「在室」。誰も2.6日間ずっと同じ場所で静止し続けない。**明らかな誤検知（張り付き）**だった。

**原因**: ベースラインを一度凍結すると、その後の**室温の日内変化**（昼は暑く夜は涼しい）に基準が追従できない。凍結した古い基準に対して `object_raw` が「基準+マージン」を超えたまま延々と張り付き、解除条件にも一生引っかからなくなる。**「凍結」そのものが原因**だった。

**修正**: 凍結をやめ、**非対称EMA常時追従**（2.4）に変更。下げは速く（離脱を即検知）、上げは遅く（静止保持＋永久ラッチ防止）。

**再検証（同じログで再replay）:**

| 指標 | 凍結案 | 非対称追従（採用） |
|---|---|---|
| 「静止在室」判定の割合 | 53% | **15.4%** |
| 最長の連続在室 | 2.6日 | **75.5分** |
| 120分以上の連続 | 多数 | **0件** |

夜間（深夜1〜4時）の点灯率も2〜4%まで下がり、生活実感に合う形になった。

> **教訓**: 「もっともらしい設計」ほど、**本番に出す前に過去の実データで再生（replay）して裏を取る。** 机上のテスト（pytest）は緑でも、現実の長期挙動は別。ログを28日分貯めてあったからこそ、2.6日バグを本番前に潰せた。「データが貯まるまで実装を確定しない」方針（[[feedback_data_driven_patience]]）が効いた瞬間。

### 4.2 トレードオフ表

| 案 | 内容 | 採否 |
|---|---|---|
| 固定しきい値 | 「object_raw < ○○ なら在室」 | ❌ 室温で空室値が動くため破綻 |
| ベースライン凍結 | 在室中は基準を固定 | ❌ 室温ドリフトで2.6日張り付き |
| **非対称EMA常時追従** | 下げ速・上げ遅で基準を常時更新 | ✅ **採用**。保持と復帰を両立 |
| ToFセンサー追加 | 距離で部屋スケールの追従 | 保留（ハード未購入・別件） |

### 4.3 やらなかったこと（意図的に）

- **ファームウェアの改造**: しなかった。生データ `object_raw` は元から取れていたので、gateway側だけで完結。焼き直しのリスク・手間を避けた。
- **しきい値/係数のダッシュボード露出**: 今回は定数のまま。まずは正しく動くことを優先。実行時調整したくなったら後で足せる（フォローアップ候補）。
- **ソファ等の死角を無理に拾う**: しなかった。物理的な視野・距離の限界で、ソフトでは埋められない（ToF待ちの領域）。**直せる範囲（視野内の席まわり）に正直に絞った。**

## 5. 実機での最終確認（E2E）

このマシン（razer-server）自体が gateway の実行機で、リポジトリを直接動かす形（editable install）なので、`sudo systemctl restart stackchan-gateway` で新コードが反映される。

| 確認項目 | 結果 |
|---|---|
| 静止保持 | 恵梨子席（弱め）で**9分静止しても在室を維持**。従来なら消えていた**約309秒分を救済**。 |
| 武装ゲート | 接近で温度差+186が出ても、動き未確認のうちは**あえて非検知**（壁の誤検知防止が機能）。 |
| 離脱解除 | 席を立った瞬間に温度が空室値へ落ち、**即座に解除・誤った張り付き0**。 |
| 室温追従 | 計測30.9℃→E2E32.3℃のドリフトを基準が追従。固定しきい値なら破綻していた領域。 |

弱め位置の恵梨子席ですら保持できた（本命1m席はさらに強い）。**狙い通りの動作を実機で確認。**
