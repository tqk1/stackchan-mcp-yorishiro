## 1. 全体像

### 1.1 何をしたか（一言で）

スマホから開ける**スタックちゃんの操作盤（ダッシュボード）**を、機能を足しながら使いやすく
育てました。音量・聞き取り・マイク感度・近接センサー・首の角度・表情・台座LED・通知…と、
バラバラに増えていく操作を**整理された1画面**にまとめ、最後に人間工学的に仕上げました。

5フェーズの中身を一言ずつ:

| フェーズ | やったこと | flash | コミット |
|---|---|---|---|
| 1 | 操作を**カテゴリ別7カード**に再編＋「デザインの型」確立 | 不要 | 不要(*) |
| 2 | **画面の明るさ + 台座LED**の制御UIを追加（LEDは3状態に拡張） | 不要 | gateway要 |
| 3 | **近接センサーの反応モード**3択＋トグル化、LED明るさ/横並び | 1回 | gateway要 |
| 4 | サーバータブに Codex/Gemini 利用率 → 調査の末**両方スキップ** | — | — |
| 5 | **人間工学的仕上げ**（並び替え・折りたたみ・状態表示・タッチ性） | 不要 | 不要(*) |

(*) ダッシュボード本体（`dashboard.html`）は **git 管理外**なので、編集した瞬間が即デプロイ＝コミット不要。
firmware を変えた時だけ flash（マイコンへの書き込み）が要ります。

### 1.2 データの流れ（この章だけは丸暗記する価値あり）

操作盤を理解する鍵は「ボタンを押すと信号がどこを通ってマイコンに届くか」です。

```
[スマホ/PCブラウザ : dashboard.html]
   │  HTTP                ボタン → fetch('/control/volume', {volume:50}) など
   ▼
[status_api.py : 8080]   … HTMLを配る係 + 薄い中継（プロキシ）
   │  HTTP (127.0.0.1:8767)
   ▼
[gateway http_server.py : 8767]   … control.py が「今の設定値」を覚えている
   │  WebSocket MCP (JSON-RPC)
   ▼
[firmware : M5Stack CoreS3]   … set_brightness / set_all / StartListening …
```

- **status_api(:8080)** は「受付の人」。ブラウザに HTML を渡し、`/control/*` の注文を
  奥（gateway）へ素通しするだけの薄い係。
- **gateway(:8767)** は「設定を覚えている人」。音量やLED色を `control_state.json` に書き留め、
  マイコンが再接続したら覚えていた値を入れ直す。
- **firmware** は実際に画面の明るさを変えたりLEDを光らせたりする「現場」。

### 1.3 2か所に分かれた「記憶」（二段の永続化）

設定が電源を切っても消えない仕組みは、**2か所**に分かれています。ここを混同しがちなので図解します。

```
firmware の NVS（マイコン内の「電源を切っても消えない手帳」）
  └ 画面の明るさ / 近接モード・しきい値 / 首の中立姿勢
      → マイコン自身が責任を持って保存。gateway は「表示用の控え」を持つだけ

gateway の control_state.json（PC側のファイル）
  └ 音量 / ミュート / マイク感度 / LED色3スロット / LED明るさ
      → マイコンに保存場所が無いものを、PC側が代わりに覚えておく
```

> **教訓**: 「どちらが本当の記憶か」を最初に決めておくと、再接続時にどちらの値で
> 上書きするか迷わない。明るさは firmware が本家、LED色は gateway が本家、と役割を固定した。

## 2. 採用した技術・部品の解説

### 2.1 ダッシュボード = 「1枚で完結する操作盤アプリ」

- **何か**: `dashboard.html` という**1ファイル**に HTML・CSS・JavaScript を全部入れた操作画面。
- **なぜ必要か**: スタックちゃんの設定を、いちいちコードを書かずスマホから変えたいから。
- **喩え**: エアコンのリモコン。ボタン（スライダー）を押すと本体（マイコン）が反応する。
  リモコン自体は薄っぺらい板で、賢い処理は本体側にある。
- **使った場面**: 全フェーズ。フェーズ1で「板のレイアウト」を整え、2〜3で「ボタン」を増やし、
  5で「押しやすさ」を仕上げた。

### 2.2 タブ切替 = 「1枚の紙を2画面ぶん使う」

- **何か**: 「サーバー」「スタックちゃん」の2タブ。画面下のナビで切り替える。
- **仕組み**: 両方のカードは**最初からHTMLに全部置いてある**。`display:none/block` で
  見せる/隠すを切り替えるだけ（`.tab-page.active`）。ページの再読み込みは起きない。
- **喩え**: 下敷きを差し替えるのではなく、**1枚の紙に2枚ぶん書いておいて、見たい方だけ照明を当てる**。
- **賢い点**: 非アクティブなタブはサーバーへの問い合わせ（ポーリング）を止めて通信を減らす
  （`if (activeTab === 'stackchan') ...`）。

### 2.3 ポーリング = 「定期的に様子を聞きに行く」

- **何か**: 一定間隔でサーバーに「今どうなってる？」と聞いて表示を最新化する仕組み。
- **なぜ必要か**: マイコンの接続状態や録音レベルは刻々と変わるが、向こうから教えてはくれないから。
- **喩え**: 鍋を火にかけて、30秒ごとに蓋を開けて中を確認する。
- **使った場面**: 温度/利用率は30秒ごと。マイク入力レベルは**録音中だけ**約120ms(秒8回)の高速ポーリング、
  録音が終わったら止める（負荷を無駄にかけない）。

> **教訓**: ポーリングは「必要な時だけ・必要な速さで」。常時高速で叩くとサーバーもバッテリーも疲れる。

### 2.4 「操作中ガード」 = 「人が触っている間は勝手に書き換えない」

- **何か**: スライダーをドラッグ中に、裏のポーリングが古い値で表示を上書きしないための仕掛け。
- **仕組み**: `scTouching.vol = true` のような旗を立て、ポーリング側は旗が立っている要素を更新しない。
  指を離す（`change`）と旗を下ろして実際に送信。
- **喩え**: 誰かが書き込み中のホワイトボードを、他の人が消さないように「使用中」の札を掛ける。

### 2.5 CSS の「デザインの型」 = 「同じ部品を使い回す」

- **何か**: フェーズ1で決めた再利用パーツ。`.row`(ラベル＋値の行) / `.row-val`(大きい現在値) /
  `.slider` / `.icon-btn`(小ボタン) / `.btn-primary`(緑の主要アクション) / `.sc-ava`(顔アバター)。
- **なぜ必要か**: 機能を足すたびに見た目を作り直すと、バラバラで二度手間。型に載せれば一貫する。
- **喩え**: レゴの基本ブロックを決めておき、新しい機能は同じブロックで組む。
- **使った場面**: フェーズ2のLED・明るさも、3の近接も、全部この型に載せた。だからフェーズ5は
  **大改造せず微調整で済んだ**（「骨組み先 → 最後に仕上げ」方針の成果）。

### 2.6 NVS = 「電源を切っても消えない手帳」（マイコン側）

- **何か**: Non-Volatile Storage。ESP32 マイコンの中にある、電源OFFでも消えない小さな保存領域。
- **使った場面**: 画面の明るさ、近接モード/しきい値、首の中立姿勢。マイコンが自分で書き込む。
- **対比（PC側）**: gateway の `control_state.json` は同じ役割を**PC のファイル**でやっている版。

### 2.7 WebSocket MCP（既出・要点だけ）

gateway とマイコンは **WebSocket（繋ぎっぱなしの内線電話）** で常時つながり、その上で
**MCP（道具を呼び出す共通言語）** を喋ります。ダッシュボードの注文は最終的に
`esp32.call_tool("self.screen.set_brightness", {...})` のような**道具の呼び出し**に化けてマイコンに届きます。
詳しくは `docs/phase-b-report.md` を参照。

### 2.8 OAuth usage API（フェーズ4の主役）

- **何か**: Anthropic が提供する「Claude Code の利用率（5時間枠・7日枠の%とリセット時刻）」を返す専用窓口。
- **仕組み**: `fetch_usage.py` が cron（定期実行）でこの窓口を叩き、`~/cc-usage.json` に保存 →
  `status_api` が `/status` に同梱 → ダッシュボードが棒グラフ表示。
- **フェーズ4の肝**: **OpenAI(Codex) と Google(Gemini) には同等の窓口が無い**。だから
  「Claude と同じ形式の利用率カード」は原理的に作れなかった（→ スキップ）。

## 3. 工程の流れ（フェーズ別の時系列）

### フェーズ1: 骨組み整備＋デザインの型（2026-06-14）

巨大な1カードに13項目がベタ並びだった状態を、**機能カテゴリ別の7カード**へ引っ越し。

- やったこと: `#tab-stackchan` の中身を `<section class="card">` 単位に再編。
  接続バッジを全体状態としてタブ最上部へ。
- **重要原則**: JavaScript は `getElementById('sc-xxx')` で部品を探すので、**IDさえ保てば
  どのカードに置いても動く**。このフェーズは純粋な「DOMの引っ越し＋見出し付け」。
- ユーザーから「崩れは無いがデザインがつまらない」とのFB → その場で**デザインの型を確立**し、
  音量＋ミュートを1行に統合、大きい現在値、顔アバター（接続中は目が緑）を導入。「よくなった」と承認。

> **教訓**: 機能を足す前に「器（カテゴリ）」と「部品の型」を先に決めると、後が楽。
> これがプロジェクト全体を貫く「骨組み先」方針。

### フェーズ2: 画面明るさ + LED（2026-06-14）

firmware に**既にあった**ツール（明るさ・台座LED）を、gateway の HTTP層とダッシュボードに繋いだ。
**firmware は無変更＝flash 不要**。

- gateway `control.py`/`http_server.py` に `POST /control/brightness`・`POST /control/led` を追加。
- 調査で判明: **明るさは firmware が NVS に自動保存**（音量と違う）。gateway側は表示用の控え。
- ユーザー提案で **LED を3スロットに拡張**: idle(通常)/listening(聞き取り)/hermes(思考中) を
  各色設定可＋「試」点灯ボタン。会話中に `apply_led_state(slot)` で色が遷移する。

### フェーズ3: 近接モード + LED明るさ/横並び（2026-06-14、flash 1回）

当初「音量200 + 近接listen」予定 → **音量200は実現不可と判明し除外**（事件簿1参照）。

- 近接センサーの反応を **3択モード**（reflex=首上げ / listen=手かざしで会話 / off）に。デフォルト listen。
- listen は **tap と同等のトグル**（かざす→録音開始 / もう一度→送信）。
- LED に**全体の明るさ**スライダー（firmwareに輝度概念が無いので gateway で r/g/b に係数を掛ける）。
- ダッシュボードの LED を **3列横並び**に。
- firmware を flash（書き込み）して実機E2E、ユーザー「全体的にいい感じ」。

### フェーズ4: Codex/Gemini 利用率 → 両方スキップ（2026-06-15、コードなし）

「サーバータブに Claude と並べて Codex・Gemini の利用率を出す」予定だったが、**計画通り
まず取得手段を調査** → 両方に障害があり、ユーザー判断でスキップ（事件簿3参照）。

### フェーズ5: 人間工学的仕上げ（2026-06-15、HTML-onlyで）

積み上がった7カードを「使い勝手」だけ整えた。スコープは**フル案**だが HTML-only 境界を維持。

| 記号 | 変更 | 狙い |
|---|---|---|
| A | 録音状態を**ヘッダーの状態ピル**に常時表示（接続/🎙録音中） | どのカードを見ていても録音中が分かる |
| B | カードを使用頻度で**3グループ再編**（よく使う/調整/設定・詳細）＋小見出し | スクロール最短化 |
| C | LED色設定を**初期折りたたみ**（既存の開閉部品を再利用） | 重い設定を畳んで一覧性UP |
| D | 首「デフォルトに保存」に**確認ダイアログ＋警告色** | 不可逆操作の誤爆防止 |
| E | ボタン類を**タッチ44px**に | スマホで押しやすく |
| F | レスポンシブ改善（幅の上限・狭画面でLED2列） | 端末幅に追従 |
| G | サーバータブの利用率を**主従の階層**に（5時間枠を主役） | 即効で効く枠を強調 |

## 4. 設計判断の記録（なぜそうしたか / しなかったか）

### 4.1 事件簿1: 音量200が出せなかった

- **症状**: 「もっと音量を上げたい（200まで）」という要望。
- **調査**: コーデックのソース（`esp_codec_dev.c`）を読むと、ボリュームカーブは `vol=100 → 0dB`
  （最大）で、**`vol >= 100` は 0dB にクリップ**。アンプ(AW88298)の上限も 0dB。
- **原因**: **100 が既に物理的な最大音量**。200 を渡しても 100 と同じ音。
- **修正**: スライダー上限は 100 据え置き。デジタル増幅は音が歪むので不採用。
- **教訓**: > 「上限を上げたい」要望は、まず**物理/仕様の天井**を確認する。
  ソフトの数字を増やしても、ハードの天井は超えられない。

### 4.2 事件簿2: LEDが60秒で勝手に消える問題

- **症状**: 設定したLED色が、会話の約60秒後に消えることがある（懸念）。
- **調査**: firmware の `set_indicator`（インジケータ点灯）は、呼ぶたびに**約60秒後に自動で
  リセットするタイマー**を張る仕様（idle-settle）。
- **原因**: 会話中に `set_indicator(青)` を使っていたため、そのタイマーが居残る。
- **修正**: ハードコードの青を撤去し、**色付きの状態は全て `set_all`（タイマーを張らない方）**で出す
  ように統一（フェーズ2の3スロット化で実施）。→ gateway がタイマーを一切張らなくなり解消。
- **教訓**: > 同じ「光らせる」でも、裏に**副作用（自動リセット）が付く道具**と付かない道具がある。
  常時表示には副作用の無い方を選ぶ。

### 4.3 事件簿3: Codex/Gemini の利用率が取れなかった

- **症状**: Claude と同じ形式で Codex・Gemini の利用率を並べたい。
- **調査**: Claude Code は `OAuth usage API` で枠%を返すが、**OpenAI(Codex)には同等の公式APIが無い**
  （ローカルの `~/.codex/` にも累積トークン数はあるが利用率%は無い）。Gemini の利用額は
  **Cloud Billing → BigQuery Export → SQL** が事実上唯一の経路で、GCP の設定が重い。
- **判断**: Codex=**スキップ**（取得不可）、Gemini=**見送り**（設定コストに見合わず・現状Gemini未使用）。
- **温存**: ダッシュボードの利用率カードのパターン（`setUsage`等）は無傷。将来取得手段ができたら
  `fetch_usage.py` の出力に `codex:{...}` キーを足すだけで流用可能。
- **教訓**: > 「他がやれてるなら自分もやれる」とは限らない。**データの取得手段の有無**を
  実装前に確認する。無ければ無駄なUIを作らず、受け皿だけ残して撤退する。

### 4.4 フェーズ5の「フル案だが HTML-only 境界」

フェーズ5のフル案には「**思考中（Hermes処理中）**の可視化」が含まれていた。だが調査で
gateway は思考中フラグ（`voice_turn_active`）を `/control/status` に**公開していない**と判明。
表示するには gateway の改修（→コミット＋テスト）が必要で、「フェーズ5＝HTMLだけ」の境界を越える。

| 案 | 内容 | 採用 |
|---|---|---|
| HTML-only 維持 | 接続＋録音だけ状態ピルに。思考中は後日 | ✅（ユーザー選択） |
| gateway拡張 | `voice_state` を公開し思考中も表示 | 見送り（境界を越える） |

> **教訓**: 「dashboard.html は編集即反映・コミット不要」という身軽さは、gateway/firmware に
> 触れた瞬間に消える（コミット＋テスト＋検証が必要になる）。**身軽さを保てる範囲**を意識して切る。

### 4.5 やらなかったこと（意図的に）

- **セクションの大改造**: 7カード構成は概ね妥当なので、並べ替えとグループ見出しに留めた。
- **独自UI部品の量産**: フェーズ5の新規CSSは `.group-label`/`.btn-warn`＋録音パルスのみ。
  折りたたみは**既存の開閉部品**（首パッドで使っていた `.ctl-toggle`/`.pad-body`）を再利用。
- **range（スライダー）の自前装飾**: iOS の標準スライダーは既に指で押しやすいので触らず。

## 5. 用語集

| 用語 | 一言で | 喩え |
|---|---|---|
| ダッシュボード | スマホで開く操作盤（1つのHTMLファイル） | エアコンのリモコン |
| status_api(:8080) | HTMLを配り、注文を奥へ中継する受付 | 受付の人 |
| gateway(:8767) | 設定を覚え、マイコンに道具を呼ばせる頭脳 | 設定を覚えている執事 |
| firmware | マイコンの中で動く現場のプログラム | 実際に手を動かす現場作業員 |
| WebSocket | 繋ぎっぱなしの双方向通信 | 内線電話（かけっぱなし） |
| MCP | 道具を呼び出す共通言語(JSON-RPC) | 「○○して」と頼む共通の言い回し |
| NVS | マイコン内の消えない保存領域 | 電源を切っても消えない手帳 |
| control_state.json | gateway 側の設定ファイル | PC側の控え帳 |
| ポーリング | 定期的に様子を聞きに行く | 鍋の蓋を定期的に開ける |
| 操作中ガード | 触っている間は上書きしない旗 | 「使用中」の札 |
| デザインの型 | 再利用するCSS部品群 | レゴの基本ブロック |
| 状態ピル | ヘッダー常駐の状態バッジ | 受付の「営業中/準備中」札 |
| レスポンシブ | 画面幅に応じて崩さない設計 | 伸縮するゴムバンド |
