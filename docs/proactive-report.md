# 自発判断層 振り返りレポート — StackChan が自分から「おはよう」「おやすみ」を言う器をつくる

> **このレポートの使い方**: StackChan が、話しかけられていないのに**自分から**
> 挨拶し、時間帯に合わせて見た目（モード）を切り替える仕組みを作った全工程を、
> 後から読み返して理解に変えるための学習用ドキュメントです。分からない箇所が
> 出たら、このファイルごと Claude や Gemini に貼り付けて「ここを詳しく」と
> 聞いてください（章7にコピペで使える質問例があります）。
>
> 対象期間: 2026-06-22（自発会話の土台）〜 2026-06-24（モード自動切替＋実機E2E）
> 対象コミット: `cd7b7b5`（ブランチ `feature/proactive`）
> 当時の生記録: `docs/worklog/2026-06-22-proactive.md` / `docs/worklog/2026-06-24-proactive-mode-switch.md`
> 前提レポート: `docs/tmos-verification-report.md`（在室を判定するセンサーの検証）/ `docs/multiturn-report.md`（会話が続く器）

## 1. 全体像

### 1.1 何をしたか（一言で）

**「部屋の状態が変わった瞬間」をきっかけに、StackChan が自分から一言挨拶し、
おやすみ／つうじょう のモードに着せ替えるようにした。**

これまでの StackChan は「触ったら反応する」受け身（リアクティブ）でした。
今回はそこに、**自分からきっかけを作って動く（プロアクティブ）** 振る舞いを足しました。
ただし「夫婦の会話に割り込まない」のが最優先なので、暴走しないよう何重もの
安全装置を通しています。

### 1.2 3つの挨拶の地図

StackChan が見ているのは「部屋の状態」です。在室センサー（TMOS）と時刻から、
部屋は次の3状態を行き来します（在室状態マシン。詳しくは tmos レポート参照）。

```
  ABSENT（不在）  ─── 帰ってきた ──→  ACTIVE（在室・活動時間帯）
                                          │  ↑
                              夜になった │  │ 朝になった
                                          ↓  │
                                      QUIET（在室・就寝時間帯）
```

この「矢印（＝状態の変化）」のうち、意味のある3本に挨拶とモード切替を割り当てました。

| 変化（矢印） | いつ | 言うこと | 着せ替えるモード |
|---|---|---|---|
| ABSENT → ACTIVE | 帰宅した | 「おかえり」 | **つうじょう**（明るい・喋れる）|
| QUIET → ACTIVE | 朝起きた | 「おはよう」 | **つうじょう** |
| ACTIVE → QUIET | 夜になった | 「おやすみ」 | **おやすみ**（暗い・消音）|

> **教訓**: 「いつ喋るか」を時計やタイマーで決めるのではなく、**部屋の状態が
> 変わった瞬間**に結びつけた。これにより「ただ時間が来たから喋る」のではなく
> 「帰ってきたから」「寝る時間になったから」という**意味**のある発話になる。

### 1.3 全体のデータの流れ（構成図）

```
[在室センサー TMOS] ──(5秒ごとに読む)──→ [PresenceMonitor (presence.py)]
                                              │ 状態が変わった瞬間だけ通知
                                              ▼
                                   [ProactiveSpeaker (proactive.py)] ← 今回の主役
                                     ├ ① ダッシュボードのトグルは ON か？
                                     ├ ② この変化は挨拶対象の3本か？
                                     ├ ③ 安全装置（会話中じゃない？等）を全部通るか？
                                     ├ ④ Hermes に「状況」を伝えて一言もらう ──→ [Hermes Agent]
                                     └ ⑤ 喋る → 一拍おく → モードを着せ替える ──→ [StackChan 本体]
```

ポイントは **「観測（目）」と「判断（口）」を分けた** こと。部屋を見るのは gateway
（機械的に高速で）、何と言うかを決めるのは Hermes（言葉の意味を分かる頭脳）です。

## 2. 採用した仕組みの解説

### 2.1 観測と判断の分離 — 「見張り番」と「あいさつ係」を分ける

- **何か**: 「部屋を見る役」と「言葉を決める役」を別々の担当にする設計。
- **なぜ必要か**: 部屋を見るのは1日中・5秒おきの高頻度作業。これを毎回 Hermes（頭脳）に
  やらせると、問い合わせが1日何千回にもなり、お金と時間が爆発する。逆に「何と言うか」は
  言葉の意味が分かる Hermes にしか決められない。だから役割を分けた。
- **喩え**: マンションの**管理人さん（見張り番）**と**住人（あいさつ係）**。管理人は
  ずっとロビーを見ていて、「誰か帰ってきた」と気づいたら住人に内線するだけ。挨拶の言葉は
  住人が考える。管理人に気の利いた挨拶を毎回考えさせない。
- **使った場面**: gateway が在室の「意味ある変化」だけを検出し、その瞬間にだけ Hermes へ
  「帰宅したみたい。一言どうぞ」と頼む。

### 2.2 状態遷移フック — 「変わった瞬間だけ鳴る呼び鈴」

- **何か**: 部屋の状態が**変化した瞬間**にだけ、登録しておいた処理を呼び出す仕組み
  （`register_on_state_change`）。
- **なぜ必要か**: 「今ACTIVEです」を5秒ごとに聞かされても困る。知りたいのは
  「ACTIVE に**なった**」瞬間だけ。変化点だけを教えてもらえば無駄がない。
- **喩え**: **ドアの開閉センサー**。ドアが開いている間ずっと鳴り続けるのではなく、
  「閉→開」に変わった瞬間にピンポンと一度鳴る。
- **使った場面**: `PresenceMonitor` が状態を更新するとき、前回と違えば登録済みの
  `ProactiveSpeaker` に `(古い状態, 新しい状態)` を渡して呼ぶ。

```python
# presence.py（要点）
def _set_state(self, new, *, notify=True):
    old = self._state
    self._state = new
    if notify and new != old and self._on_change:   # 変わった時だけ
        asyncio.get_running_loop().create_task(self._fire_change(old, new))
```

### 2.3 モードプリセットの流用 — 「いつもの設定セット」を一発で着せ替え

- **何か**: ケンジさんがダッシュボードで作った「おやすみ」「つうじょう」という
  **設定の詰め合わせ（プリセット）** を、状態変化のたびに丸ごと適用する。
- **なぜ必要か**: 「夜モード」は音量0・ミュート・画面暗く・LED消灯…と複数項目の集合。
  これを毎回コードに書くと、設定変更のたびにコードを直すことになる。すでにある
  「保存された設定セット」を呼び出すだけにすれば、コードは設定の中身を知らなくていい。
- **喩え**: 照明の**「シーン」ボタン**。「映画モード」を押すと、照明・カーテン・音量が
  まとめて切り替わる。一つ一つ操作しない。
- **使った場面**: 夜の変化で「おやすみ」プリセット、朝・帰宅で「つうじょう」プリセットを
  `apply_preset` で丸ごと適用。プリセットの中身（何を暗くするか）は StackChan 任せ。

> **教訓**: 新機能を「ゼロから作る」より「既にある部品を組み合わせる」方が、
> 変更が小さく・壊れにくい。ケンジさんが先にダッシュボードでモードを作っていたから、
> 自発判断層は「いつ着せ替えるか」だけを足せばよかった。

### 2.4 発話とモード切替の順序 — ミュートが言葉を飲み込まないように

- **何か**: 「喋る」と「モード着せ替え」のどちらを先にやるかを、ミュートで困らない
  順番に固定したこと。
- **なぜ必要か**: 「おやすみ」モードは**消音**する。もし消音を先にやってから
  「おやすみ」と言ったら、声が消えて聞こえない。逆に朝はミュート解除を先にしないと
  「おはよう」が聞こえない。
- **喩え**: 寝る前の段取り。「おやすみ」と**声をかけてから**電気を消す。朝は
  **電気をつけてから**「おはよう」と言う。順番を逆にすると気まずい。
- **使った場面**:
  - 夜（ACTIVE→QUIET）= **喋る → 着せ替え（消音・暗く）**
  - 朝・帰宅（→ACTIVE）= **着せ替え（明るく・消音解除）→ 喋る**

### 2.5 「間（ま）」— 一拍おいてから着せ替える

- **何か**: 喋り終わってからモードを切り替えるまでに、1.5秒の小さな待ち時間を挟む。
- **なぜ必要か**: 実機で見たら、喋った**直後**に画面が暗くなるのが**唐突**だった
  （ケンジさんの実機フィードバック 2026-06-24）。一拍おくと自然に感じる。
- **喩え**: 「おやすみ」と言って、**ひと呼吸おいてから**部屋の電気を消す感じ。
  言い終わった瞬間にパチンと消すと事務的。
- **使った場面**: 喋り↔着せ替えの間に `await asyncio.sleep(1.5)` を挟む。秒数は
  環境変数 `STACKCHAN_PROACTIVE_MODE_DELAY_S` で調整可、`0` で即時。

> **教訓**: 機能としては「喋る＋着せ替え」で完成だが、**自然に感じるか**は実機で
> 人が見ないと分からない。pytest では「間が入っている」ことしか確かめられず、
> 「1.5秒が気持ちいいか」は実機 E2E でしか分からなかった。

### 2.6 多層ガード — 会話に割り込まない安全装置

- **何か**: 「今は喋っちゃダメ」な状況を何重にもチェックし、一つでも引っかかれば沈黙する。
- **なぜ必要か**: 設計原則①「夫婦の会話に割り込まない」が絶対だから。自発発話は
  便利だが、暴走すると一番嫌われる機能になる。
- **喩え**: 発言する前の**指差し確認**。「会話中じゃない？録音中じゃない？さっき喋った
  ばかりじゃない？夜中じゃない？今日もう喋りすぎてない？」を全部 ✓ してから口を開く。
- **使った場面**: `_skip_reason()` で順にチェック。会話中(voice_turn)・録音中・音声再生中・
  マルチターン継続中・在室ゲート・直前に話しかけられた後のクールダウン・1日の上限・
  同じ挨拶の連発防止（refire）。**「おやすみ」だけは夜間ガードを例外**にしている
  （後述の事件簿2参照）。

### 2.7 二段の安全スイッチ — env とダッシュボードトグル

- **何か**: 機能を ON/OFF する栓が2つある。環境変数 `STACKCHAN_PROACTIVE`（大元）と、
  ダッシュボードの「🗣️自発会話」トグル（実行時）。
- **なぜ必要か**: 大元の栓は「そもそもこの機能を載せるか」、トグルは「今この瞬間
  喋らせるか」。env を設定しないと完全に無効（opt-in）で、安全側に倒している。
- **喩え**: 家の**元栓**（env）と各部屋の**蛇口**（トグル）。元栓を開けて初めて、
  蛇口で水を出したり止めたりできる。
- **使った場面**: env 未設定なら `ProactiveSpeaker` 自体が作られない。トグルは
  実行中にいつでも切れる緊急停止ボタン（ダッシュボード OFF が env ON に勝つ）。

## 4. 設計判断の記録

### 4.1 モードを別機能にする vs 挨拶に相乗りさせる

| 案 | 内容 | 評価 |
|---|---|---|
| A: 独立した時計で別途モード切替 | 22:00 ちょうどにモードだけ切り替える専用タイマー | 在室状態と二重管理になる |
| **B: 挨拶と同じ遷移に相乗り** ✅ | 既にある状態遷移に「挨拶＋モード」を載せる | 仕組みが1本化・安全装置も共用 |

B を採用。会話中などのガードを**モード切替にも自動で効かせられる**のが大きい
（会話中に勝手に画面を暗くしない＝原則①）。

### 4.2 「おやすみ」を夜間ガードの例外にする

自発発話には「夜中は喋らない（22:00-06:30）」というガードがある。だが「おやすみ」は
**まさに夜の始まり（22:00）に言う挨拶**なので、このガードに引っかかると永久に言えない。
→ 「おやすみ」遷移だけ夜間ガードを免除した。朝の「おはよう」は6:30（ガード終了直後）なので
そのままで問題なし。

### 4.3 帰宅でも「つうじょう」を適用する

夜にミュート状態で帰宅したケースで音が戻らないと困るので、帰宅（ABSENT→ACTIVE）でも
「つうじょう」を適用して必ず音・明るさを戻す（ケンジさん確定）。昼の短い外出→即帰宅なら
実質何も変わらない（同じ設定の再送）。

### 4.4 やらなかったこと（意図的に）

- **常時マイクで聞き取る（VAD）**: 採用しない（原則①）。きっかけは「状態変化」だけ。
- **語尾切れ対策のガード遅延**: 入れなかった。音声送出が実時間ペーシングなので語尾は
  切れないと実機で確認（事件簿2）。「間」は別目的（自然さ）で入れた。
- **モード切替を会話ガードから外す**: やらない。会話中に勝手に画面を暗くするのは
  原則①違反なので、モード切替も会話ガードを通す。
- **境界ぴったりに会話中だった時の救済**: しない。その1回はスキップ許容（ケンジさん確定）。
  将来データを溜めて精度を上げる方針（章6）。

## 5. つまずきの事件簿

### 事件簿1: 設定をいじっても StackChan が喋らない（notify=False の罠）

- **症状**: 実機テストで「睡眠時間帯」をいじって夜の状態を作っても、proactive が発火しない。
- **調査**: `update_config`（しきい値変更）のコードを読むと、設定変更時に状態を
  **即時更新するが `notify=False`**（＝呼び鈴を鳴らさない）になっていた。
- **原因**: これは**意図的な設計**だった。「ダッシュボードでしきい値を再調整しただけ」を
  「帰宅／起床」と誤認させないため、設定由来の状態変化では observer を呼ばない。
- **修正**: テストの誘発方法を変えた。**「睡眠時間帯の境界を1〜2分先に置く」**と、
  設定変更時点では状態が変わらず（silent）、その後**実時刻が境界を跨いだ通常の見回り
  （5秒ごとのポーリング）で本物の遷移が発火**する。これは本番とまったく同じ経路。
- **教訓**:

> **教訓**: 「設定変更による状態変化」と「現実の出来事による状態変化」は別物として
> 扱うのが正しい。テストのためにこの正しい設計を曲げるのではなく、**現実の出来事の方を
> 人工的に作る**（時計が境界を跨ぐ状況を用意する）のが筋の良いやり方だった。

### 事件簿2: ミュートが「おやすみ」の語尾を切らないか？

- **症状（の懸念）**: 夜は「喋る→消音」の順。消音が早すぎると「おやすみ」の語尾が切れるのでは？
- **調査**: 音声を送る `send_pcm_audio` を読むと、音の断片を**実際の再生スピードに合わせて
  1個ずつ送っている**（再生が終わる頃に送信も終わる）。
- **原因**: つまり「喋り終わり」とほぼ同時に処理が戻るので、その後の消音が語尾を切る危険は
  ごく小さい（本体内部の僅かなバッファ末尾だけ）。
- **修正**: 先回りでガード遅延は入れず、**実機で確認**。語尾切れは起きなかった（「〜ましょう」
  まで聞こえた）。ガードは不要と確定。
- **教訓**:

> **教訓**: 「危なそう」で先回りして複雑な対策を入れるより、まず実機で確かめる。
> 結果、語尾切れ対策は不要だった。一方で「間が欲しい」という**別の**要望が実機で出た
> ＝機械の正しさ（pytest）と、人が自然に感じるか（実機）は別の軸。

### 事件簿3: トグルが「動かない」＝実は反映されていなかった

- **症状**: 第一段階でダッシュボードにトグルを足したのに「動かない」。
- **原因**: 動いている gateway が**古いコードのまま**だった。サービスは
  「editable install（ソースを直接読む方式）」なので、コードを書いても**再起動するまで
  古いコードが動き続ける**。さらに大元の env も未設定だった。
- **修正**: `sudo systemctl restart stackchan-gateway` で再起動 → 反映。
- **教訓**:

> **教訓**: 「コードを直した」と「動いているプログラムに反映された」は別。
> 常駐サービスは**再起動して初めて新コードになる**。テストが通っても、実機が古いままなら
> 何も変わっていない。

## 6. 用語集

| 用語 | 一言で | 喩え |
|---|---|---|
| プロアクティブ / リアクティブ | 自分から動く / 受け身で反応する | 自分で話しかける人 / 聞かれたら答える人 |
| 状態遷移 | 状態が別の状態へ変わること | ドアが「閉→開」に変わる |
| 状態遷移フック | 変化の瞬間に処理を呼ぶ仕組み | ドアの開閉センサーのピンポン |
| observer（オブザーバ） | 変化を知らせてもらう登録先 | 「変わったら内線して」と頼んだ相手 |
