## 1. 全体像

### 1.1 何を作ったか（一言で）

StackChan は部屋に人が居るか（在室か）を TMOS という熱センサーで見張っていて、
その結果を毎ポーリング（約5秒おき）に1行ずつログファイルに書き溜めています。
これまで「在室判定がちゃんと働いているか？」の確認は、ケンジさんの手元にある
使い捨てスクリプト（`scratch/analyze_presence.py`）を**手で走らせて目視**していました。

Phase 2 でやったことは、一言でいうと:

> **その手作業の集計を StackChan 本体（gateway）に組み込んで、在室判定の「健康診断」を
> いつでも・自動で出せるようにした。**

具体的に手に入った体験:

```
・ダッシュボードに「📊診断」タブが増えた。開くと在室判定の健全性が一覧で出る
  （滞在時間の内訳・在室判定のクッキリ度・在室中の「谷間」・推奨しきい値・時間帯別の在室率）
・gateway が毎日1回、その日の診断レポートを自動でファイルに書き残す（md と json）
・「不在判定までの猶予（absent_after_s）は何秒が妥当か」を数字の根拠つきで提案してくれる
  （ただし提案するだけ。勝手に変えはしない＝最終判断はケンジさん）
```

そして、この開発の途中で**実データを見たからこそ気づけた設計バグ**を1つ潰しました。
これが今回いちばんの学びどころなので、章4「事件簿」でじっくり書きます。

### 1.2 全体の流れ（データの旅）

```

                                   │ 1行ずつ追記
                                   ▼
              ~/.stackchan/presence_log.jsonl  ← 生ログ（約12万行/7日分）
                                   │
                    ┌──────────────┴───────────────┐
                    │ 末尾N日だけ読む                │ （新規）
                    ▼                               ▼
        presence_report.build_report()      _maybe_write_daily_report()
        ＝集計の「計算だけ」する部品          ＝毎日1回ファイルに書く部品
                    │                               │
        ┌───────────┴────────────┐                  ▼
        ▼                        ▼      ~/.stackchan/presence_reports/2026-06-25.md (+.json)
```

## 2. 採用した技術・考え方の解説

それぞれ「何か → なぜ必要か → 喩え → 使った場面」の順で説明します。

### 2.1 自己診断レポート — 「健康診断の結果票」

**何か**: センサーが溜めた生ログを集計して、「在室判定がうまく働いているか」を
数字でまとめたもの。

**なぜ必要か**: 在室判定には `absent_after_s`（人が消えてから「不在」と判断するまでの猶予秒数）
のような**しきい値**があります。これが短すぎると、トイレに立っただけで「いなくなった」と
誤判定して StackChan が黙ります。長すぎると、本当に外出してもいつまでも「居る」と思い込みます。
適切な値は**実際の生活データを見ないと決められません**。その判断材料を毎回手で集計するのは
面倒なので、本体に組み込みました。

**喩え**: 健康診断の結果票です。体重・血圧・血糖値…と項目別に数字が並び、
「基準値より高め」のような所見が付く。あれの「在室判定版」を作りました。

**使った場面**: ダッシュボードの「📊診断」タブと、毎日自動で残るレポートファイル。

### 2.2 純粋関数 — 「材料を入れたら必ず同じ料理が出る自販機」

**何か**: 「同じ入力を渡したら、必ず同じ出力を返し、それ以外の副作用（ファイル書き込み・
時刻取得・通信）を一切しない関数」のこと。今回の集計部品 `build_report()` がこれです。

**なぜ必要か**: テストが劇的に楽になるからです。もし集計関数が中で
「`~/.stackchan/presence_log.jsonl` を開いて、今の時刻を取って…」と動いていたら、
テストのたびに本物のログファイルと現在時刻を用意しないといけません。
代わりに「ログの中身（リスト）」と「今の時刻」を**引数で外から渡す**形にすると、
テストは合成データを渡すだけで全パターンを再現できます。

**喩え**: 自販機です。「コーヒーのボタン（入力）」を押せば必ず「コーヒー（出力）」が出る。
中で勝手に在庫管理ノートに書き込んだり、外の天気を見て味を変えたりしない。
だから「このボタンを押したらこれが出る」を確実にテストできます。

```python
# presence_report.py — 時刻すら引数で受け取る（now=）。中で time.time() を呼ばない
def build_report(records, *, now, tz=JST, current_absent_after_s=None):
    ...
    return { "basic": ..., "valleys": ..., "recommendation": ... }
```

**使った場面**: 集計の全ロジック。おかげでテストは「こういうログならこの数字」を
39本、合成データだけで書けました。本物の12万行ログは最後の検証で1回使うだけ。

> **教訓**: 「計算」と「入出力（ファイル・時刻・通信）」を分けると、計算側はテストし放題になる。
> 入出力は薄い殻（今回は `presence.py` 側）に寄せ、中身の計算は純粋関数に閉じ込める。

### 2.3 谷間（valley）— 「在室なのに presence が途切れている時間」

**何か**: 「部屋に人が居る（在室）区間の中で、センサーが presence を見失って連続している時間」。
今回の主役の指標です。

**なぜ必要か**: TMOS は「動いている熱」しか拾えません。人が静止すると一時的に見失います。
この「見失い時間（谷間）」が `absent_after_s` より長いと、在室中なのに「不在」に倒れます。
つまり **谷間の長さの分布こそが、`absent_after_s` を何秒にすべきかの直接の根拠**です。

**喩え**: 留守番電話の「無音の長さ」です。会話中でも数秒の沈黙はある。
でも沈黙が30秒続いたら「電話切れた？」と思う。その「どれくらいの沈黙までは
まだ繋がっているとみなすか」が `absent_after_s`、実際に起きた沈黙の長さが谷間です。

**使った場面**: 推奨しきい値の算出。ただしここに大きな落とし穴があり、章4で詳述します。

### 2.4 パーセンタイル（p99 など）— 「下から数えて何％目の値」

**何か**: データを小さい順に並べたとき「下から99%の位置にある値」が p99。
中央値（median）は p50（ちょうど真ん中）です。

**なぜ必要か**: 平均値は外れ値に弱い（1個だけ極端な値があると引っ張られる）。
「谷間はだいたいどれくらいまで伸びるか」を知るには、平均より
「99%の谷間はこの長さ以内に収まる」という p99 のほうが役に立ちます。

**喩え**: テストの順位です。「上位1%」と言われたら、ほぼ最高得点層を指す。
p99 は「ほぼ最大級だが、極端な1件には引っ張られない代表値」と思ってください。

**使った場面**: 推奨しきい値 = 谷間の p99 × 1.25（余裕係数）を 30秒丸め。

### 2.5 asyncio.to_thread — 「重い作業は別の人に回して受付は止めない」

**何か**: 時間のかかる処理を別スレッド（別の作業員）に投げて、本体の応答を
止めないようにする仕組み。

**なぜ必要か**: 12万行のログを読んで集計するのに約0.6秒かかります。gateway は
同時に StackChan 本体との通信や他のダッシュボード操作も捌いています。集計を本線で
やると、その0.6秒の間ほかが全部固まります。

**喩え**: 受付窓口です。重い書類整理を頼まれたら、自分でやらずに奥の人に渡して、
受付は次のお客さんを捌き続ける。集計（重い書類整理）は別スレッドへ、
窓口（gateway 本線）は止めない。

```python
# http_server.py — 集計は別スレッドへ逃がす
report = await asyncio.to_thread(monitor.build_report, days=days)
```

**使った場面**: `GET /control/presence/report` の窓口。実測で7日分は1.27秒（中継込み）でした。

### 2.6 冪等（べきとう）と atomic write — 「1日1回・書きかけは見せない」

**何か**:
- **冪等**: 同じ操作を何回やっても結果が1回分にしかならない性質。
- **atomic write**: ファイルを「下書き（一時ファイル）に全部書いてから一気に本番名へ差し替える」
  書き方。書いている途中の中途半端なファイルが他から見えない。

**なぜ必要か**: 日次レポートは「1日1回」書きたい。でもポーリングは5秒おきに走ります。
毎回書いたら無駄だし、書いている最中に読まれたら壊れたファイルを掴むかもしれません。

**喩え**:
- 冪等 = エレベーターの「↑」ボタン。何回連打しても呼ばれるのは1回。
- atomic write = レポートを別紙に清書し終えてから、机の上の旧版とスッと差し替える。
  書きかけの紙を机に置きっぱなしにしない。

**使った場面**: 日次レポート。「その日のファイルが既にあれば書かない（冪等）」＋
「一時ファイルに書いてから `os.replace` で差し替え（atomic）」。
再起動しても二重には書かれません。

## 3. 工程の流れ（時系列）

計画を M1〜M6 のマイルストーンに割って、順に積み上げました。

| 段 | やったこと | 検証 |
|---|---|---|
| **M1** | 集計の純粋関数 `presence_report.py`（6種の集計＋Markdown整形）。テスト39本 | pyted緑・ruff clean |
| **M2** | `GET /control/presence/report` の窓口＋ログ末尾N日読み | テスト緑 |
| **M3** | 毎日1回の自動レポート書き出し（冪等・atomic・env でON/OFF） | テスト緑 |
| **M4** | ダッシュボード「📊診断」タブ＋中継(status_api)の窓口許可 | JS構文チェック |
| **M5** | 実機デプロイ（2サービス再起動）＋ライブ検証 | 200応答・日次生成確認 |
| **M6** | この学習レポート | — |

### M1 の中身（6種の集計）

`build_report()` が返す診断は6グループ:

1. **基本**: 期間・サンプル数・データの鮮度（最後の記録が何秒前か）
2. **サンプル間隔**: 記録の間隔・欠測（gateway が止まっていた疑いのある30秒超の穴）
3. **state別滞在**: active(活動)/quiet(就寝)/absent(不在)/unknown(不明) の滞在時間と割合
4. **presence分離度**: 在室時と不在時の presence 値が**どれだけクッキリ分かれているか**
5. **谷間**: 在室中の presence 途切れ時間（全体＋ACTIVE限定）
6. **時間帯別**: 1時間ごとの在室率・室温

### M2 の工夫（末尾N日だけ読む）

12万行を毎回全部読むのは重い。`?days=7` のように期間を指定し、
「`ts_unix`（記録時刻）が `今 - N日` より新しい行だけ採用」して絞ります。
この「時刻で足切り」のやり方は、既に gateway にあったログ掃除関数
（`event_log.rotate_old_entries`）と同じ流儀を踏襲しました。
**新しく発明せず、既にある作法に合わせる**のは、後から読む人の負担を減らす大事な判断です。

### M5 のライブ検証（実機で確かめた）

再起動後、実際に叩いた結果:

```
GET :8080/control/presence/report?days=7  → HTTP 200 / 1.27秒
  samples=117700（=168.0時間=ちょうど7日。期間絞りが効いている証拠）
  separation=good（在室判定はクッキリ分かれている）
```

## 4. 事件簿: 推奨しきい値が「現状値 × 1.25」を返すだけの罠（打ち切り＝censoring）

ここが今回いちばんの学びです。**実データを見たから気づけた**設計バグの話。

### 症状

推奨 `absent_after_s` を「ACTIVE 中の谷間の p99 × 1.25」で計算する初版を書きました。
合成データのテストは全部通りました。ところが、念のため本物の12万行ログで動かしてみたら、
こんな数字が出ました:

```
ACTIVE限定の谷間: p99 = 1079秒, max = 1079.4秒
現在の absent_after_s = 1080秒   ← p99 も max も、ほぼ完全に一致！
推奨値 = 1079 × 1.25 ≈ 1350秒
```

谷間の最大値が、たまたま現在のしきい値（1080秒）にピッタリ張り付いている。
偶然にしては出来すぎです。

### 調査と原因

理由を追ったら、**構造的に絶対そうなる**ことが分かりました。

在室判定エンジンの作りを思い出してください。ACTIVE（活動中）に presence が
`absent_after_s`（1080秒）の間ずっと途切れると、状態は **ABSENT（不在）に切り替わります**。
切り替わった瞬間、その区間はもう「ACTIVE」ではなくなる。

つまり **ACTIVE 区間の谷間は、定義上 1080秒を超えられない**のです。
1080秒に達した時点で ACTIVE が終わってしまうから。これを統計用語で
**右側打ち切り（right-censoring）** と呼びます。

> **喩え**: 2メートルまでしか目盛りのない身長計で「人類の最大身長」を測ろうとするようなもの。
> 2m20cmの人が来ても、目盛りは2mで頭打ち。記録だけ見ると「最大身長は2m」に見える。
> でもそれは身長計の限界であって、人類の本当の最大身長ではありません。

だから「ACTIVE 谷間の p99（≒1080）× 1.25」は、結局
**「今のしきい値 × 1.25」を返しているだけ**。これを採用して1350秒に上げると、
次は谷間が1350秒まで伸びて、また「1350×1.25」を推奨する…と
**毎回じわじわ上がり続ける（ラチェット）**。推奨値として機能していませんでした。

### 修正

正しい母数は「しきい値に達する前に在室へ戻った谷間（resolved）」だけです。
天井に張り付いた谷間（censored）は「本当に出ていったのか、ただセンサーが見失っただけか」
区別できないので、推奨値の計算からは外し、**別指標として件数だけ報告**します。

実データで分けたら、はっきりしました:

```
ACTIVE谷間 315個 ＝ resolved 286個 ＋ censored 29個
  censored の値: 1075〜1079秒 にギッシリ密集（＝まさに天井に張り付き）
  resolved だけの p99 = 925秒  →  推奨 = 925 × 1.25 ≈ 1170秒
```

推奨が「1350秒（現状×1.25）」から「1170秒（実際の在室中ドロップアウトに基づく値）」に変わりました。
しかも「ACTIVE 中に29回、presence が天井まで途切れて不在判定された（真の離席か死角かは要観察）」
という、それ自体が有用な所見も副産物で得られました。

### なぜ手元スクリプトでは気づかなかったか

`scratch/analyze_presence.py` は数字を画面に並べるだけで、ケンジさんが目で見ていました。
p99 と max が両方1079という不自然さは、数字の羅列の中だと埋もれます。
今回「この数字から推奨値を**自動で計算する**」ところまで踏み込んだので、
「現状値×1.25を返すだけ」という無意味さが浮き彫りになりました。

> **教訓**: 「あるしきい値で状態が切り替わる系のログから、そのしきい値を推定する」と、
> 必ず打ち切り（censoring）が混入する。母数を打ち切り前（resolved）に限定し、
> 打ち切り件数は別指標で出す。そして —— **合成データのテストが通っても安心しない。
> 本物のデータで一度動かすと、構造的なバグが姿を現す**。

## 5. 設計判断の記録

「なぜそうしたか」「なぜそうしなかったか」を残します。

### 採用したトレードオフ

| 判断項目 | 選んだ案 | 理由 |
|---|---|---|
| 集計の置き場所 | ✅ 純粋関数の新モジュール `presence_report.py` | 入出力と分離してテスト容易（章2.2）|
| 出力形態 | ✅ 窓口(API)＋ダッシュボード＋日次自動保存 の全部 | 即時に見たい＆履歴も残したい（ケンジさん合意）|
| しきい値の扱い | ✅ 提案するだけ・自動適用しない | 設計原則の human-in-the-loop（最終判断は人）|
| 推奨の母数 | ✅ resolved 谷間のみ（章4）| 打ち切りを含めるとラチェットして無意味 |
| 日次保存のトリガー | ✅ ポーリングに相乗り＋日付変化で1回 | heartbeat の既存パターンを踏襲・新タスク不要 |
| 重い読み込み | ✅ `asyncio.to_thread` で別スレッド | 本線(gateway)を固めない（章2.5）|

### やらなかったこと（意図的に）

- **推奨値の自動適用（ワンクリック反映ボタン）**: あえて付けませんでした。
  設計原則「自発的な変更は人の承認を挟む」を守るため。適用 UI は Phase 3 に回します。
  代わりに推奨値を機械可読（`recommended_absent_after_s`）で持たせ、将来の承認 UI に橋渡し済み。
- **古い日次レポートの自動削除**: 1ファイル数KBで28日でも約140KB。誤差なので未実装。
- **時間帯別の全期間表示**: ダッシュボードは直近48時間まで（7日だと168行で長すぎる）。
  全量は日次レポートのファイルに記録。**「省略したことを画面に明記」**して、
  見ている人が「これで全部」と誤解しないようにしました。
- **OpenAI 等の外部 API での集計**: 在室データは私生活そのもの。ローカル完結を貫く。

## 6. 用語集

| 用語 | 一言で | 喩え |
|---|---|---|
| 在室判定エンジン | 部屋に人が居るかを判定する仕組み（`presence.py`）| 部屋の見張り番 |
